# CLAUDE.md

Guidance for Claude Code (and any engineer) working in this repository.

## Project

**Bawi Shopping** — a professional multi-vendor fashion marketplace for the United States, modeled on the Amazon Marketplace business model. Independent fashion brands and boutiques ("sellers") list clothing and accessories; customers can buy from multiple sellers in a single cart; the platform takes a commission on every transaction; seller payouts run through Stripe Connect.

**Current phase: eleven vertical slices implemented.**
1. Customer registration (storefront) and seller authentication with server-derived vendor association (seller portal).
2. Seller application intake, admin review/approval/rejection, and seller account activation — spanning a new `seller-application` backend module, a new `audit-log` module, and a new `apps/admin` frontend.
3. Seller product creation, admin review/approval/rejection, and public product viewing — spanning a new `product-listing` backend module (layered on Medusa's native product/variant/inventory/pricing modules), new pages across all three frontends, and the `packages/i18n` localization foundation.
4. Product discovery, categories, search, and filtering — admin category management (parent/child, translated names) on top of Medusa's native `product-category` module plus a new `category-translation` module; a public `SearchService`-backed discovery API (`/categories`, `/products`, `/brands`); a storefront homepage, category pages, and a search/filter/sort page with a mobile filter drawer and cursor-based "Load more" pagination; new `ProductCard`/`ProductGrid` components in `packages/ui`.
5. Merchant-of-record decision recorded (see below) plus Stripe Connect seller onboarding — a new `business-config` module (centralized commission/shipping/return/etc. inputs and launch-safety feature flags) and Stripe Express account linking with idempotent webhook handling, entirely testable against a network-free fake Stripe client.
6. Multi-vendor shopping cart — layered on Medusa's native `cart` module: server-side variant/price/inventory/approval resolution on every add and refresh (`src/cart/`), guest carts identified by an opaque cart id (httpOnly cookie on the storefront, forwarded as a header to the backend), a login/register-time merge workflow, and a storefront cart page/icon/add-to-cart control. Vendor ownership is tracked internally (line-item `metadata.vendor_id`) but never serialized to any response.
7. Merchant-of-record checkout and multi-vendor order splitting — a new `marketplace-order` module (`src/modules/marketplace-order/`, combining the parent `Order`, per-seller `VendorOrder`, and `VendorOrderItem` in one module, same one-module-multiple-models precedent as `seller`) plus a mock tax adapter (`src/tax/`) and a platform-account Stripe PaymentIntent client (`src/payments/stripe-payment-client.ts`). Checkout re-validates the cart server-side, reserves inventory, and creates one PaymentIntent for the full cart total; a single Stripe webhook receiver (extended, not duplicated) splits the paid order into one `VendorOrder` per seller - each snapshotting its own commission rate/amount, shipping/tax share, and fulfillment deadline/code - only after capture succeeds, then finalizes the inventory deduction and clears the cart. No guest checkout (`order.customer_id` is `NOT NULL` by design); no money is transferred to sellers yet (payouts are a later slice). Storefront checkout uses Stripe's Payment Element (`@stripe/react-stripe-js`) - card data never reaches this app's own frontend or backend code.
8. Private vendor fulfillment and delivery — a new `fulfillment-privacy` module (`src/modules/fulfillment-privacy/`: `Courier` - its own actor type, admin-provisioned; `PickupCode`/`TrackingCode` - unguessable, per-vendor-order, issued together once a seller marks an order ready for pickup; `FulfillmentCodeRedemption` - a single atomic unique-index claim table enforcing single-use/replay-protection for both code types). `VendorOrder` gained lifecycle timestamps and `assigned_courier_id`. The full lifecycle: seller marks preparing → ready for pickup (codes minted) → admin assigns a courier → courier redeems the pickup code (seller-shown) to confirm pickup → courier starts delivery → courier redeems the tracking/delivery code (customer-shown, proof of delivery) to confirm delivery. Seller, courier, and customer each get a purpose-built, privacy-scoped view (`src/fulfillment/`) built to exclude the other parties' identity/PII by construction, not by after-the-fact filtering - sellers never see customer name/phone/email/address; customers never see vendor identity/pickup address/private SKU; couriers see only their one active assignment's handoff details. The courier portal lives inside `apps/admin` under `/courier/*` with its own session cookie - not a sixth full app, given how narrow the role's access is (see `docs/DECISIONS.md`). Every code issuance/consumption, status change, and courier read of an assignment's detail is audit-logged.
9. Commission ledger, seller payouts, returns, refunds, and disputes — a new `seller-finance` module (`src/modules/seller-finance/`: `CommissionLedgerEntry`, `Payout`/`PayoutLineItem`, `ReturnRequest`, `OrderRefund`, `Dispute`). A commission ledger entry is created at checkout capture (net of shipping/tax, which stay Bawi's own revenue) and becomes payable once its transfer-hold period passes; balance buckets (pending/available/paid/disputed) are derived at read time, never stored. Admin-triggered payout batches create idempotent Stripe test-mode Transfers per seller. Customers can cancel before a seller starts preparing, or request a return after delivery (damaged/defective/incorrect/customer-remorse); a seller's approval issues a test-mode Stripe refund, a proportional commission reversal, and restocks inventory for restockable reasons. Stripe disputes (`charge.dispute.*` webhooks) freeze the affected ledger entry until resolved. Seller payout dashboard (`apps/seller-portal` `/finance`, `/returns`) and admin financial dashboard (`apps/admin` `/finance`, `/finance/disputes`, `/finance/returns`) round out the slice. All live-money feature flags remain `false`.
10. Notifications and account completion — transactional email fires through Medusa's native `notification` module (the `notification-local` provider - logs only, until `real_email_enabled`), with a thin custom `notification_inbox` module layered on top for a per-recipient, queryable in-app notification center the native module doesn't provide. Eight existing workflows now send a notification at the moment they already perform their side effect (order confirmation, shipment/delivery updates, return status changes, refunds, payouts, seller-application approval/rejection) — see `apps/storefront` `/account`'s notifications section and `apps/seller-portal` `/notifications`. Saved addresses (storefront `/account`) and admin user/invite management (`apps/admin` `/team`) needed no new backend code at all — both are Medusa native functionality (`/store/customers/me/addresses`, `/admin/users`, `/admin/invites`), wired up frontend-only. Seller staff invites (`apps/seller-portal` `/staff`) reuse the existing seller-application activation-token mechanism to add `catalog_manager`/`order_fulfiller`/`analyst` co-workers under one seller.
11. Full content translation and production readiness — a new `product_translation` module (own moderation lifecycle: seller drafts/submits per locale, admin approves/rejects, mirroring `product-listing`'s own shape) makes product titles/descriptions translatable into the same five locales as categories; the public product-detail route resolves an approved translation for `?locale=` with English fallback, same pattern as category translations. Seller-portal `/products/:id/translations` and admin `/translations` round out the moderation UI. A CI pipeline (`.github/workflows/ci.yml`) now runs lint/typecheck/unit tests/build on every PR, plus a second job running the full backend integration suite against a real Postgres service container. The pre-existing `apps/backend/src/scripts/check-production-readiness.ts` script (built ahead of when it was needed, in an earlier phase) reports every business-config value still at a placeholder default and the state of every real-money/real-communication feature flag - see `docs/DECISIONS.md` for its current output and what genuinely remains before a production launch.

All are built, tested (unit, integration, component, E2E), and passing (see `docs/DECISIONS.md` for the small number of integration-test files this development machine's memory pressure has prevented running to completion - documented as deferred infrastructure issues, not code defects). Seller-application/product-listing approve-reject, category create/update/delete, cart line-item mutations, checkout/order-capture, the fulfillment lifecycle, the commission/payout/return/refund/dispute lifecycle, every notification-triggering action, and product-translation approve/reject all run as Medusa workflows with compensating rollback where meaningful (see `docs/DECISIONS.md`) rather than direct service calls from route handlers. Every session-scoped page across all three frontends exports `dynamic = "force-dynamic"` (see `docs/DECISIONS.md` for why). This completes `docs/PRD.md`'s first-release feature list, aside from the production-infrastructure items `docs/DECISIONS.md` documents as genuinely out of reach for an agent working in a local sandbox (real load testing, a real staging deployment/soak test, and any business/legal decision behind a remaining `is_placeholder: true` business-config value) - see `docs/IMPLEMENTATION-PLAN.md` for what a human operator still needs to do before a real production launch.

**Approved but not achievable by an agent in this environment:** real load testing, a real staging deployment/soak test, and production infrastructure provisioning (a real CI runner beyond the checked-in config, a real cloud environment) - see `docs/DECISIONS.md` and `docs/IMPLEMENTATION-PLAN.md` for exactly what remains for a human operator. **Permanent product codes and private vendor SKUs are already implemented** (product-catalog slice, above) - they were built ahead of the rest of private fulfillment specifically to avoid a schema rework later, and that bet paid off: the fulfillment slice above needed no product/inventory schema changes. **Merchant-of-record is RESOLVED: Bawi Shopping is the merchant of record for every transaction.** Customers purchase from Bawi, not directly from a vendor; Bawi controls the customer relationship, payment, receipts, customer service, tracking, returns, refunds, disputes, and seller payment. Payment architecture: customer charges on Bawi's Stripe platform account, Stripe Connect **Express** accounts for sellers, **Separate Charges and Transfers** (never Destination Charges, never a vendor as the customer-facing merchant), Stripe **test mode only** until an explicit production-launch approval. See `docs/DECISIONS.md` for the full decision and `docs/PAYMENTS.md` for mechanics.

**Business configuration is centralized, not hardcoded.** Commission rate, seller-transfer hold period, return window, seller prep deadline, shipping fee, free-shipping threshold, service area, cart expiration/max-quantity, and similar business inputs live in the `business-config` module (category/key/value, audit-logged, admin-editable) with explicit development/staging defaults - every default is flagged as a placeholder pending real business/legal approval (cart's own two entries are a genuine v1 scope decision, not a pending approval - `is_placeholder: false`). Feature flags (`live_payments_enabled`, `real_transfers_enabled`, `real_payouts_enabled`, `real_refunds_enabled`, `real_tax_calculation_enabled`, `real_email_enabled`, `real_sms_enabled`, `real_courier_booking_enabled`, `promotional_codes_enabled`) all default `false` and gate every code path that would otherwise move real money or send a real communication. See `docs/DECISIONS.md`.

**Localization (i18n foundation being built now, full translations gradual):** six supported locales — English (`en-US`, fallback), Amharic (`am`), Tigrinya (`ti`), Afaan Oromo (`om`), Simplified Chinese (`zh-CN`), Spanish (`es`). Translations live in a table separate from the base product record (`product_id` + `locale`), never per-locale columns or duplicate product rows. Seller/AI-submitted translations require Bawi approval before going live — same moderation shape as products. See `docs/ARCHITECTURE.md` §12, `docs/DESIGN-SYSTEM.md` §12, `docs/PRD.md` §9.24.

**Approved architecture — confirmed, not a proposal.** Medusa + PostgreSQL + Stripe Connect is the commerce backend and system of record. **Supabase (Auth, Database, or Storage) is not used anywhere in this project** — see `docs/DECISIONS.md` for why this needed to be stated explicitly. If a generic instructions file or dependency suggestion implies otherwise, this file and `docs/DECISIONS.md` win.

## Non-negotiable architecture rules

These rules constrain every future change, not just the initial build:

1. **Modular monolith, not microservices.** One backend deployable (Medusa), organized into isolated modules with clear boundaries. Do not split into services prematurely.
2. **Every seller-owned record carries a `vendor_id`.** No exceptions, no nullable escape hatches for seller-scoped tables.
3. **Sellers can never read or write another seller's private data.** Enforced at the application/authorization layer on every query path, not just in the UI.
4. **Never store raw card data.** All card handling goes through Stripe (Elements/Payment Element + Stripe Connect). The platform never touches PANs, CVCs, or full card numbers.
5. **Payment webhook handlers must be idempotent.** Stripe (and any future PSP) can and will redeliver events; handlers must dedupe by event ID before applying side effects.
6. **Every important marketplace action is audit-logged**: seller approval/rejection, product changes, price changes, order state changes, refunds, payouts, admin overrides, role/permission changes.
7. **All schema changes go through migrations.** No manual DDL against any environment.
8. **Business logic does not live in React components.** Storefront, seller portal, and admin portal are thin clients over the Medusa backend's modules/workflows/APIs.
9. **One shared design system** powers the storefront, seller portal, and admin portal — no divergent component libraries.
10. **No unnecessary libraries.** Prefer what Medusa, Next.js, and Stripe already give you before reaching for a new dependency.
11. **Stay inside approved first-release scope** (see `docs/PRD.md` §"First-Release Feature List" and §"Deferred Features"). Anything not listed there is out of scope until explicitly re-prioritized.
12. **Vendor and customer identities are never exposed to each other.** Neither party sees the other's real name or contact details through any API response, UI, or notification. All fulfillment communication, tracking, returns, and packaging are Bawi-controlled — there is no direct seller-to-customer or customer-to-seller channel. See `docs/DECISIONS.md` and `docs/SECURITY.md` §11.

## Stack summary

- **Backend / commerce engine:** Medusa 2.x (Node/TypeScript), PostgreSQL — no Supabase, no other BaaS
- **Frontends:** Next.js (App Router) + TypeScript — customer storefront (`:3000`), seller portal (`:3001`), admin portal (`:3002`) (three separate apps, all built). Server Components by default, Server Actions for mutations, Route Handlers for webhooks/external APIs.
- **Validation:** Zod, at every Server Action boundary and every Medusa API route boundary
- **Shared UI:** `packages/ui` (Button, Input, Select, Textarea, Checkbox, FormField, StatusBadge — grows per `docs/DESIGN-SYSTEM.md`), imported by all three frontends. v1 is light-mode only — dark mode is explicitly deferred (see `docs/DESIGN-SYSTEM.md` #2 and `docs/DECISIONS.md`); don't reintroduce a `prefers-color-scheme: dark` override without also making the component set dark-mode-aware.
- **Background jobs:** dedicated worker process (Medusa subscribers/workflows + queue), separate from the API process — not yet built
- **Payments:** Stripe Connect (Express accounts), Stripe Payment Element on the storefront — not yet built
- **Media:** object storage (S3-compatible) for product images — not yet built
- **Search:** live-query Postgres adapter (no index table, see `docs/DECISIONS.md`) behind a swappable `SearchService` interface (`packages/search-contract`), with a ranked/indexed Postgres or Algolia adapter planned for a later phase — v1 implemented
- **Monorepo:** npm workspaces + Turborepo (see `docs/DECISIONS.md` for why npm rather than the originally-planned pnpm)
- **Testing:** Vitest + React Testing Library + Playwright for both Next.js apps; Medusa's own Jest-based tooling for the backend (unit, module-integration, HTTP-integration) — see `docs/DECISIONS.md`
- **Local dev database:** Postgres.app (PG16) on port `5544` — see `docs/DECISIONS.md` for why not Homebrew

## Working conventions

- Read `docs/ARCHITECTURE.md` before adding any new module or crossing an app boundary.
- Read `docs/DATABASE.md` before adding or changing a table; every migration needs a corresponding entry there.
- Read `docs/SECURITY.md` before writing any query that touches seller- or customer-scoped data.
- Check `docs/DECISIONS.md` before assuming a doc's originally-planned tech choice (pnpm, Homebrew Postgres, etc.) is what's actually running — several were changed for environment reasons during implementation.
- Update the relevant doc in the same change that changes the behavior it describes — these docs are meant to stay current, not become stale artifacts.

## Local development

See [`README.md`](README.md) for full setup steps. Summary:

- Postgres.app (PG16) running on port `5544`; databases `bawi_shopping_dev` and `bawi_shopping_test` already exist locally.
- `apps/backend`: `npm run dev` (or `npx medusa develop`) starts the Medusa server on `:9000`. Run `npx medusa db:migrate` after adding a migration. Create an admin user with `npx medusa user -e you@example.com -p <password>`.
- `apps/storefront`: `npm run dev` on `:3000`. Needs `.env.local` with `MEDUSA_BACKEND_URL` and `MEDUSA_PUBLISHABLE_KEY` (see `.env.example`).
- `apps/seller-portal`: `npm run dev -- -p 3001` on `:3001`. Needs `.env.local` with `MEDUSA_BACKEND_URL`.
- `apps/admin`: `npm run dev -- -p 3002` on `:3002`. Needs `.env.local` with `MEDUSA_BACKEND_URL`. Log in with a user created via `medusa user` above.
- E2E tests (`npm run test:e2e` in any frontend app) assume the backend is already running against a migrated database. The seller-application journey test spans `apps/seller-portal` and `apps/admin` in one spec (`apps/seller-portal/e2e/seller-application.spec.ts`) and starts both dev servers itself.
