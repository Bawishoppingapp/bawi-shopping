# Bawi Shopping — Technical Decisions

A running log of decisions that aren't obvious from reading the code, in the order they were made. Newest at the bottom.

---

## Commerce backend stays Medusa; Supabase is not used

**Date:** first implementation session (user registration vertical slice).

**Decision:** Medusa + PostgreSQL remains the commerce backend and system of record, exactly as specified in `docs/ARCHITECTURE.md` and `docs/DATABASE.md`. **Supabase Auth, Supabase Database, and Supabase Storage are not used anywhere in this project.**

**Why:** A separate, generic "Project Instructions" template was supplied mid-project assuming a Supabase-based stack (Supabase Postgres + Auth + Storage, a single Next.js app under `src/features`). That conflicts directly with the already-decided architecture: Medusa owns its own Postgres schema via its own module system and its own `auth` module (customer/seller_user/admin actor types), which is structurally incompatible with Supabase owning identity and enforcing access via Postgres RLS. The user was asked and explicitly chose to keep Medusa.

**How to apply:** If a future instructions file, template, or dependency suggestion mentions Supabase (or any other backend-as-a-service for auth/db/storage), treat it as inapplicable to this project unless the user explicitly says otherwise. Non-backend conventions from that instructions file (Zod for validation, Vitest/RTL/Playwright for tests, `src/features` organization, Server Components by default, Server Actions for mutations) do still apply and don't conflict with Medusa — only the identity/data-ownership layer was in question.

## `seller_user` is a custom Medusa auth actor type, not a separate identity provider

**Decision:** Sellers authenticate through Medusa's own `auth` module using a third actor type, `seller_user`, alongside Medusa's native `customer` and `user` (admin) actor types. There is no separate auth provider (Auth0, Supabase Auth, custom JWT issuer, etc.) for sellers.

**Why:** Medusa v2's auth module is actor-type-agnostic by design — `/auth/:actor_type/:auth_provider/*` works for any actor type string without extra registration. The only real work is linking a freshly-created `auth_identity` to our own business entity (`SellerUser`, in the custom `seller` module) via `app_metadata.seller_user_id`. Once that link exists, Medusa's own JWT issuance (`generateJwtTokenForAuthIdentity` in `@medusajs/medusa`) sets the token's `actor_id` claim directly to that `seller_user_id` — so `req.auth_context.actor_id` in an authenticated request *is* the `SellerUser` row's id, with no extra resolution step needed.

**How to apply:** Any future actor type (e.g., a hypothetical `affiliate` or `support_agent`) should follow the same pattern: a custom module owning the business entity, a `POST` flow that registers the auth identity and then sets `app_metadata.<actor_type>_id`, and route-level `authenticate(actorType, [...])` middleware (see `apps/backend/src/api/middlewares.ts`) scoping access.

## Vendor scoping for sellers: server-derived, never client-supplied

**Decision:** The seller portal never sends or trusts a `vendor_id`/`seller_id` from the client. Every seller-scoped request re-derives it server-side from the authenticated session via `GET /seller/me` (`apps/backend/src/api/seller/me/route.ts`), which reads `req.auth_context.actor_id` and looks up the corresponding `SellerUser` → `Seller`.

**Why:** This is the core tenant-isolation guarantee in `docs/SECURITY.md` §2. Verified with an integration test asserting seller A's valid session/token never resolves to seller B's vendor record, even though both exist in the same database.

**How to apply:** Every future seller-scoped Medusa API route must resolve `vendor_id` this same way (from `req.auth_context`, via the `seller` module's service) — never accept it as a path/query/body parameter for a seller-actor caller.

## Monorepo tooling: npm workspaces, not pnpm

**Decision:** The monorepo uses **npm workspaces** (root `package.json` `"workspaces"` field) instead of the originally-planned pnpm + Turborepo. Turborepo itself is still used, installed as a root devDependency and invoked via `npm run <script>` → `turbo run <script>`.

**Why:** The development machine's Homebrew installation (needed to install `pnpm` globally) is owned by a different macOS user account, and reassigning that ownership (`sudo chown`) would affect another person's environment — an action outside what this session should take unilaterally. npm ships with Node and required no additional system-level install.

**How to apply:** Use `npm install`, not `pnpm install`. Per-workspace commands use `npm run <script> --workspace=<name>` or `-w <name>`. If `pnpm` becomes available in a given environment later, migrating is possible but not required — npm workspaces satisfy every requirement in `docs/ARCHITECTURE.md` (single lockfile, per-app `package.json`, shared `packages/*`).

## Local Postgres: Postgres.app, not Homebrew

**Decision:** Local development Postgres runs via **Postgres.app** (a self-contained `/Applications` bundle, PG16), listening on port `5544`, with its own data directory at `~/.local/share/bawi-postgres`, `trust` auth for the local user.

**Why:** Same Homebrew-ownership constraint as above — `brew install postgresql` would have required `sudo chown` on another user's Homebrew prefix. Postgres.app needs no Homebrew and no sudo.

**How to apply:** Local `DATABASE_URL`s point at `postgresql://<user>@127.0.0.1:5544/<dbname>`. Two databases exist locally: `bawi_shopping_dev` and `bawi_shopping_test`. A teammate on a machine with working Homebrew access can use a standard `brew install postgresql@16` setup instead — nothing in the app depends on Postgres.app specifically, only the port/connection string in each `.env*` file.

**Update:** `max_connections` was raised from the default `100` to `300` in `~/.local/share/bawi-postgres/postgresql.conf` (requires a `pg_ctl restart -o "-p 5544 -k /tmp"` to take effect) while diagnosing an unrelated `@medusajs/test-utils` hang - see the workflow-atomicity decision below. Left at 300 going forward since it costs nothing locally and gives headroom for future in-process test tooling that opens many pools at once (Medusa's full app loader registers a separate connection pool per core module).

## A single React version across the monorepo, except Medusa's admin dashboard

**Decision:** The workspace root pins `react`/`react-dom` to `19.2.4` (matching both Next.js apps) as explicit root `devDependencies`. `apps/backend`'s own React 18 requirement (for `@medusajs/dashboard`, the admin UI bundler) resolves to its own nested `node_modules/react@18` and does not affect the root.

**Why:** Without an explicit root pin, npm's hoisting picked React 18.3.1 for the root (to satisfy the backend's admin-dashboard tooling, discovered first), which meant any workspace-hoisted testing tool (`@testing-library/react`) silently resolved React 18 while the actual Next.js apps' own code resolved their local React 19 — two React copies in one test run, breaking rendering with a cryptic "Objects are not valid as a React child" error with no meaningful stack trace pointing at the real cause.

**How to apply:** Don't remove the root-level `react`/`react-dom` devDependency pin without re-testing `apps/storefront` and `apps/seller-portal`'s Vitest suites — that pin is what keeps the frontend apps' React resolution consistent with their test tooling. `packages/ui` also carries an explicit `react`/`react-dom` devDependency for the same reason (shared UI components must resolve the same React copy the consuming app uses).

## `ajv` pinned at the workspace root

**Decision:** Root `devDependencies`/`overrides` pin `ajv` to `^8.17.1`.

**Why:** Medusa's own migration tooling (`@mikro-orm/migrations` → `umzug` → `@rushstack/ts-command-line` → `ajv-draft-04`) requires `ajv` v8's export map (`ajv/dist/core`). Without a root-level pin, a different tool in the workspace (most likely ESLint's own dependency chain) hoists `ajv` v6 to the root, and `ajv-draft-04` — which sits at the same node_modules level — resolves that v6 copy instead, breaking any command that touches Medusa's migrator (including `apps/backend`'s Jest-based integration tests, which load `@medusajs/utils` for `loadEnv`).

**How to apply:** If `apps/backend`'s tests start failing with `Cannot find module 'ajv/dist/core'` again after a dependency change, check this pin is still in the root `package.json` first before debugging further.

## Backend tests use Jest; frontend tests use Vitest

**Decision:** `apps/backend` keeps Medusa's own scaffolded Jest setup for its tests (unit + module-integration + HTTP-integration, per `docs/TESTING.md`'s levels). `apps/storefront` and `apps/seller-portal` use Vitest + React Testing Library for unit/component tests and Playwright for E2E, per the Project Instructions' testing stack.

**Why:** Medusa v2's own tooling (`@medusajs/test-utils`, migration test helpers, the `medusa` CLI's test scaffolding) is built around Jest; fighting that to force Vitest into the backend would add friction for no real benefit. The frontend apps have no such constraint, so they use the stack the user specified.

**How to apply:** Don't try to unify these into one test runner — the split is intentional and matches each side's actual framework conventions.

---

## Backend HTTP integration tests boot a real `medusa develop` child process, not `@medusajs/test-utils`' bootstrap

**Decision:** `apps/backend/integration-tests/http/seller-auth.spec.ts` starts the actual Medusa server as a child process (`integration-tests/http/test-server.js`, using `medusa develop` against the `bawi_shopping_test` database) and talks to it over real HTTP, rather than using `medusaIntegrationTestRunner` from `@medusajs/test-utils`.

**Why:** `@medusajs/test-utils`' bootstrap manages its own ephemeral-database lifecycle assumptions (via `pg-god`, expecting `DB_HOST`/`DB_PORT`/`DB_USERNAME` env vars for an *admin* connection separate from the app's own `DATABASE_URL`) that didn't line up cleanly with this project's local Postgres.app setup, and use of a `medusa develop`-forced `NODE_ENV=development` inside its own bootstrap defeated a `NODE_ENV=test`-gated approach for exposing test-only routes. The child-process approach exercises the exact same code path production traffic would (real HTTP, real signed JWTs, real Postgres) and was more reliable to get working correctly than fighting the test-utils bootstrap's environment assumptions.

**How to apply:** Two test-only API routes exist solely to support this: `POST /seller-test-support/provision` and `GET /seller-test-support/publishable-key` (`apps/backend/src/api/seller-test-support/`). Both are gated on `process.env.ENABLE_TEST_SUPPORT_ROUTES === "true"` (not `NODE_ENV`, since `medusa develop` forces `NODE_ENV=development` regardless of what's passed in) and return 404 otherwise. Any new backend integration test should reuse `test-server.js` rather than reintroducing `@medusajs/test-utils`' bootstrap, unless someone specifically resolves the env-timing issue described above.

## `"use server"` files may only export async functions

**Decision:** Constants and non-function state (`initialRegisterState`, `CUSTOMER_SESSION_COOKIE`, and the seller-portal equivalents) live in a plain `constants.ts` file per feature, separate from the `actions/*.ts` files that carry the `"use server"` directive.

**Why:** Discovered via a failing E2E test, not by inspection: a file marked `"use server"` may only export async functions — every other export type breaks Next.js's client-reference generation for that module, and the failure mode is a confusing runtime error ("The module has no exports at all") rather than a build-time type error. This is a Next.js/React Server Functions constraint, not specific to this codebase.

**How to apply:** Any new Server Action file should export *only* async functions. Initial/default state objects, cookie name constants, and shared types belong in a sibling `constants.ts` (or similar) that both the action file and the calling Client Component import from directly.

## `seller-application` is its own module, separate from `seller`

**Date:** seller-application vertical slice.

**Decision:** `SellerApplication` records live in a new custom module (`apps/backend/src/modules/seller-application`), not inside the existing `seller` module. The two are linked only by a plain `seller_id` column set on the application once approved - not a hard foreign key, not a Medusa module-link.

**Why:** Explicitly required (a pending or rejected application must never be confused with, or accidentally grant access to, a real vendor record) and it also matches how Medusa itself models "intent" vs "real entity" elsewhere (e.g., `cart` vs `order`). Keeping approval as an explicit state transition between two separate tables makes "this application does not yet have vendor access" a structural fact, not just an application-logic convention.

**How to apply:** Don't add columns to `seller_application` that duplicate `seller` fields "for convenience," and don't add a real FK constraint from `seller_application.seller_id` to `seller.id` - the relationship is deliberately loose (nullable, set once, read-only after) rather than a first-class relation, because the two entities have different lifecycles and different audiences (an application's private review fields like `rejection_reason` must never leak through any relation that a seller-facing or public query might traverse).

## Seller account activation uses a custom token, not Medusa's password-reset flow

**Date:** seller-application vertical slice.

**Decision:** Approving a `SellerApplication` creates a `Seller` + `SellerUser` with `auth_identity_id: null` and a custom `activation_token` (32 random bytes, hex-encoded) + expiry. The seller later calls `POST /seller-activation/complete` with that token + a chosen password, which creates the `auth_identity` at that point (via `authModuleService.register("emailpass", ...)`, the same call used everywhere else in this codebase for creating a password identity) and links it to the pre-existing `SellerUser`.

**Why:** Medusa's auth module has a built-in password-reset-token mechanism (`createPasswordResetToken`/`consumePasswordResetToken`), which looked like a natural fit at first glance. It was deliberately not used: those methods are designed for a user who **already has** a password to reset, and their exact semantics for an identity that doesn't exist yet were unverified and added risk for no real benefit. The custom token reuses the exact `authModuleService.register(...)` + `app_metadata` linking pattern already proven for customer registration and seller seeding (see the `seller_user` actor-type decision above), so it only relies on Medusa APIs this codebase had already exercised successfully.

**How to apply:** If a future "resend invitation" or "reset an existing seller's password" feature is built, that's the point where Medusa's real password-reset-token flow becomes appropriate (it's designed for exactly that case - an existing identity, not a not-yet-created one). Don't conflate the two flows.

## No notification/email service yet: the activation link is shown directly in the admin UI

**Date:** seller-application vertical slice.

**Decision:** `POST /admin/seller-applications/:id/approve` returns the seller's activation link (`{seller-portal}/activate?token=...`) directly in the JSON response, and the admin UI displays it in a highlighted box after approving, labeled explicitly as a stand-in.

**Why:** The Notifications module (email delivery) is still in `docs/PRD.md` §8's future-phase list - building it now to send exactly one email would be scope creep for this slice. Surfacing the link in the UI keeps the flow fully usable today (an admin can copy/paste or forward it manually) without inventing a fake email integration.

**How to apply:** When the Notifications module ships, this is one of the first templates to wire up - replace the UI display with an actual email send, keep the link generation logic (`apps/backend/src/api/admin/seller-applications/[id]/approve/route.ts`) exactly as-is, since only the delivery mechanism changes, not the token/link generation.

## Admin portal is a full Next.js app (`apps/admin`), not a Medusa Admin Extension

**Date:** seller-application vertical slice.

**Decision:** `apps/admin` is a fourth Next.js app on the same `packages/ui` design system as the storefront and seller portal - not built using Medusa's own bundled admin dashboard framework (`@medusajs/dashboard`, its own React/Vite/react-router stack, reachable at `/app` on the backend).

**Why:** `docs/CLAUDE.md` rule #9 ("one shared design system powers the storefront, seller portal, and admin portal — no divergent component libraries") and `docs/ARCHITECTURE.md`'s original 5-app plan both already called for this. Medusa's own admin dashboard is a legitimate, faster option for pure Medusa-entity CRUD (products, orders, etc.) and remains available at `/app` for anything this project doesn't build custom UI for, but seller-application review has marketplace-specific concepts (application statuses, rejection reasons, activation links) that don't fit its native admin extension points as naturally as a purpose-built page does, and using it here would have meant the admin experience diverging from the other two apps' look and feel.

**How to apply:** Keep using `apps/admin` + `packages/ui` for anything admin-facing that's specific to this marketplace's own domain (seller applications, moderation, commissions, reporting). Medusa's native `/app` dashboard is still fine to use as-is (not to be rebuilt) for pure catalog/order/customer administration once those areas exist, since re-implementing all of Medusa's own admin CRUD screens from scratch would be wasted effort - the two can coexist.

## Custom `/admin/*` routes are not automatically authenticated

**Date:** seller-application vertical slice.

**Decision:** `apps/backend/src/api/admin/seller-applications/*` routes are explicitly protected via `authenticate("user", ["bearer", "session"])` in `apps/backend/src/api/middlewares.ts` - the same pattern already used for `/seller/*`.

**Why:** It's tempting to assume everything under `/admin` is automatically gated by Medusa just because of the path prefix. Checked directly in `node_modules/@medusajs/medusa/dist/api/middlewares.js`: Medusa's own blanket `/admin*` matcher only applies `setSecretApiKeyContext` - every native admin route (customers, products, etc.) wires its own `authenticate("user", ...)` individually. A custom route under `/admin` that skips this is unauthenticated by default, not secure by default.

**How to apply:** Any new custom route under `/admin/*` must add its own `authenticate("user", ...)` entry in `middlewares.ts` - never assume the path prefix alone provides protection. This was verified with an integration test (unauthenticated request to `/admin/seller-applications` returns 401) and an E2E test (visiting `/applications` in `apps/admin` without a session redirects to `/login`).

## `model.json()` columns need a type assertion for array data

**Date:** seller-application vertical slice.

**Decision:** `SellerApplication.product_categories` (a `string[]` in practice) is typed by Medusa's model builder as `Record<string, unknown>` (the generic shape for `model.json()`), so the create call casts it: `product_categories as unknown as Record<string, unknown>`.

**Why:** The underlying Postgres column is a plain `jsonb` that happily stores an array; Medusa's TypeScript types for `model.json()` just don't model "this specific JSON column holds an array" - there's no narrower type available and adding a whole custom column type for one array field wasn't worth it for this slice.

**How to apply:** Any future `model.json()` column that stores an array (not a plain object) will need the same cast at the point of creation. This is a known, narrow gap in Medusa's typings, not a sign of a modeling mistake.

## v1 stays light-mode only, everywhere - `prefers-color-scheme: dark` removed from all three apps

**Date:** seller-application vertical slice (found during manual browser verification, not by inspection).

**Decision:** Removed the `@media (prefers-color-scheme: dark)` block from `globals.css` in `apps/storefront`, `apps/seller-portal`, and `apps/admin`. All three now render in light mode regardless of OS/browser preference.

**Why:** `docs/DESIGN-SYSTEM.md` §2 already said dark mode is deferred past v1 - but the Next.js scaffold's default `globals.css` includes a dark-mode media query that flips the page *background* to near-black while `packages/ui` components (`Input`, `Button`, etc.) use fixed `text-neutral-900`-on-white-ish classes that don't adapt. The combination produced a real, hard-to-read screen (dark background, near-black text) in any browser/OS set to dark mode - only caught by taking an actual screenshot during manual testing, not by lint/typecheck/tests. Since dark mode support isn't in scope, the fix is to stop flipping the background, not to make every component dark-mode-aware.

**How to apply:** If dark mode is ever built for real (a deliberate future decision, not this one), it needs to update `packages/ui`'s components to use theme-aware color tokens, not just restore this CSS block. Don't re-add a bare `prefers-color-scheme` override without that work happening at the same time.

## Seller-application approve/reject now runs as a Medusa workflow, not sequential `await`s

**Date:** before the product-catalog vertical slice (explicitly requested as a prerequisite - "make that flow atomic before the marketplace starts relying on approved seller records for products and payments").

**Decision:** `POST /admin/seller-applications/:id/approve` and `.../reject` no longer call `sellerModuleService`/`sellerApplicationModuleService`/`auditLogModuleService` directly in sequence. Each now delegates its writes to a `createWorkflow`/`createStep` saga (`apps/backend/src/workflows/approve-seller-application.ts`, `reject-seller-application.ts`). Every step that writes data has a compensation function that undoes it, so a failure partway through (seller created but seller_user creation fails, or the audit-log write fails after everything else succeeded) rolls back everything the earlier steps wrote, in reverse order, automatically.

**Why:** All three modules (`seller`, `seller-application`, `audit-log`) happen to share one Postgres connection in this project (`medusa-config.ts` has one `databaseUrl`), which made a raw shared-DB-transaction approach *technically* possible (Medusa's `MedusaService`-generated methods accept a `sharedContext` with a `transactionManager`). That was deliberately not used: it would mean reaching into another module's internal transaction manager mechanics across module boundaries, which breaks the modular-monolith principle that a module could theoretically sit behind a different datastore later (see `docs/ARCHITECTURE.md` §1). Workflows with compensation are Medusa's own documented, first-class answer to exactly this problem (verified against `@medusajs/core-flows`' own `createUserAccountWorkflow`/`createUsersStep` for the pattern), and this project's `medusa user` CLI already exercises the same workflow engine successfully, so no new infrastructure was needed.

**How to apply:** Any future multi-module write sequence that needs "all or nothing" semantics (e.g., the product-approval flow this decision was a prerequisite for) should follow the same shape: one step per module write, each returning `new StepResponse(result, compensationInput)`, with a compensation function for every step except the last (the last step's compensation would only run if a later step failed, and there is none). Keep read-only pre-checks (idempotency checks, uniqueness checks) in the API route before invoking the workflow - they don't need transactional rollback since they don't mutate anything.

**Testing note:** `@medusajs/test-utils`' `medusaIntegrationTestRunner` (which boots the full Medusa app in-process against a fresh ephemeral database) hung indefinitely in this local environment for reasons unrelated to this change - even a bare `pg-god` create/drop against the same Postgres instance succeeded in under a second, so the hang is somewhere inside the full app-loader boot against a brand-new, not-yet-migrated database, not a connection-pool or credentials problem (raising `max_connections` from 100 to 300 didn't help either - see the Postgres.app decision above, now updated to 300). Rollback correctness is instead verified through the project's existing real-server HTTP integration pattern (`apps/backend/integration-tests/http/seller-application.spec.ts`), forcing genuine step failures with a temporary `ALTER TABLE ... ADD CONSTRAINT force_test_failure CHECK (false) NOT VALID` on the target table for the duration of one request. Plain `GRANT`/`REVOKE` doesn't work for this because the app's local-dev DB role (`bawishopping`) is a Postgres superuser and bypasses privilege checks entirely - a `CHECK` constraint is enforced regardless of role. Don't reach for `medusaIntegrationTestRunner` again in this repo without first getting a minimal repro of that hang working standalone.

## Private-fulfillment, identity-separation, and localization requirements - documented now, built later

**Date:** immediately before the product-catalog vertical slice.

**Decision:** The following are now **approved, decided requirements** for the marketplace, captured here so the product-catalog design (and everything after it) doesn't foreclose them, even though most of the actual functionality is explicitly **not** built in the product-catalog slice:

- **Private vendor fulfillment.** Sellers fulfill their own orders, but not by shipping directly to the customer's identity - see below.
- **Vendor and customer identities remain separated.** Neither party is ever shown the other's real identity/contact details. This is a stronger, bidirectional version of the existing "seller identity must not be publicly exposed" rule in the product spec.
- **Permanent product codes.** Every product gets a permanent code, issued once, distinct from its (mutable, human-editable) slug - stable even if the product is retitled, re-slugged, or archived.
- **Private vendor SKUs.** A seller's own SKU is stored but never exposed on any customer-facing or public endpoint.
- **Temporary fulfillment codes** and **single-use, expiring pickup QR codes** - part of the future delivery/handoff flow, not built yet.
- **A `courier` role with limited order access** - sees only what's needed to complete a pickup/handoff (no customer PII beyond what a handoff requires, no seller PII, no order financials).
- **Bawi-controlled communication, tracking, returns, and packaging.** The platform is the intermediary for all buyer/seller logistics contact - there is no direct seller-to-customer or customer-to-seller channel for shipping/returns coordination.
- **Merchant-of-record is an explicitly unresolved legal/business decision.** Not decided here, not implied by anything else in this list - flagged so it isn't accidentally decided by default via whatever the payments/tax implementation ends up assuming.
- **Six supported languages:** English, Amharic, Tigrinya, Afaan Oromo, Simplified Chinese, and Spanish. **English is the fallback** whenever a translation is missing. Product translations are stored in a table **separate from the base product record** - never inline per-locale columns on `product`. **Bawi must approve** any seller-submitted or AI-generated product translation before it's shown to customers (same shape as product approval itself - translations are content, and content is moderated).

**Why:** This is the platform's core trust/privacy model (comparable to how food-delivery and gig-logistics platforms keep restaurant and customer contact details from each other) plus its target-community localization requirement (serving Amharic/Tigrinya/Oromo/Chinese/Spanish-speaking communities, not just English speakers), decided by the user ahead of building the fulfillment and localization slices so the product-catalog schema doesn't have to be reworked later to accommodate them.

**How to apply - what changes now vs. later:**
- **Changes now (product-catalog slice):** the `product` table gets a permanent `product_code` column (distinct from `slug`), and any per-variant seller SKU is treated as private data - never returned from a public/storefront-facing endpoint, same tier of sensitivity as `seller_application.rejection_reason`. The product schema does **not** grow per-locale columns - if/when translations are built, they land in their own table keyed by `product_id` + `locale`.
- **Documented, not built, in this slice:** delivery/fulfillment execution, temporary fulfillment codes, pickup QR codes, the `courier` role/portal, Bawi-mediated communication/tracking/returns/packaging, the translation UI/approval workflow, and the merchant-of-record decision. See `docs/PRD.md` §8 and the new deferred feature-spec subsections, `docs/USER-ROLES.md` §2.7, `docs/SECURITY.md` §11, and `docs/ARCHITECTURE.md` §4 module map for where each now has a placeholder.
- Don't design the product-catalog slice's authorization/response shaping in a way that would leak seller identity to customers or customer identity to sellers beyond what's already required for order fulfillment once that slice exists - the identity-separation rule is already in effect even though the fulfillment system that depends on it isn't built yet.

## Private-vendor-fulfillment model elaborated: order-level codes, per-role information scoping, sorting-hub flexibility

**Date:** immediately after the entry above, same pre-product-catalog window - the user formalized the model with more operational detail before implementation continued.

**Decision:** Refines (does not replace) the entry above. Bawi Shopping is a **private-vendor-fulfillment marketplace**: customers shop only from Bawi Shopping, never directly from a vendor. Elaborated rules:

- **Bawi controls**, not vendors: product listings, pricing, customer service, tracking, returns, receipts, and vendor communication.
- **Three distinct order-level codes** (not one) once orders exist: a temporary **fulfillment code**, a temporary **pickup code**, and a temporary **tracking code** - each scoped to its own purpose, none of them the permanent `product_code`.
- **Pickup codes are single-use and expire on collection** (event-based expiry - consumed the moment pickup is confirmed - not just a fixed time-based TTL).
- **Vendors receive, per order, only:** product, size, quantity, a preparation deadline, and pickup instructions. Never the customer's name, contact details, payment information, or delivery address.
- **Couriers receive only** the pickup and delivery information needed for their one assigned delivery - not broader account/order access.
- **Seller-facing APIs must never return customer delivery information** - not "filtered by default," an absolute rule to design and test against from the first order-related endpoint onward.
- **Vendor IDs stay server-side and private** - already this project's standing rule (`docs/SECURITY.md` §2), reaffirmed here specifically because it's what keeps a vendor from being identifiable to a customer through an API response.
- **All sensitive access and status changes are audit-logged** - reaffirms CLAUDE.md rule #6, extended explicitly to fulfillment-code issuance/consumption once that's built.
- **Returns are handled through Bawi**, never by giving a customer a vendor's address directly.
- **The architecture must support either direct courier pickup from the vendor or a future Bawi-operated sorting hub** - i.e., don't hard-code "courier always picks up at the vendor's address" into the data model; the pickup location for a given order should be a resolvable value, not an assumption baked into fulfillment-code generation.

**Why:** This is explicitly the trust model the business is built on (per the user: comparable to how gig-delivery platforms never expose restaurant/customer contact info to each other) - not a generic privacy nicety but the mechanism that lets Bawi be the merchant relationship of record for customer service, disputes, and returns regardless of which vendor fulfilled an order.

**How to apply:** Still nothing to build this slice (checkout, courier delivery, pickup QR codes, payouts, and returns remain explicitly out of scope - see `docs/PRD.md` §9.23). What changes now is how later slices must be *designed*: any future order/fulfillment schema needs separate `fulfillment_code`/`pickup_code`/`tracking_code` concepts (not one shared code), any vendor-facing order view must be built by construction to exclude customer PII (not by filtering it out after the fact), and the stock-location model already in place for this slice (`apps/backend/src/workflows/shared/default-stock-location.ts`, a single "Bawi Fulfillment Center" location) is deliberately compatible with a future sorting-hub model - it does not assume per-vendor pickup addresses. **Merchant-of-record remains an explicitly unresolved legal/business decision that must be finalized before payments are implemented** - flagged again here since it's directly load-bearing for the fulfillment model (who has legal authority over returns, who appears on receipts) and must not be implicitly decided by how the payments phase happens to be built.

## Multilingual support (six languages) formalized as a core requirement, with an i18n foundation built ahead of full translation

**Date:** immediately after the private-fulfillment elaboration above, same pre-product-catalog window.

**Decision:** Localization (first introduced as a deferred item in the earlier entry above) is now a **core, named requirement** with a locale list and concrete mechanics: English (`en-US`), Amharic (`am`), Tigrinya (`ti`), Afaan Oromo (`om`), Simplified Chinese (`zh-CN`), Spanish (`es`). Unlike the fulfillment/courier/QR-code items, the user asked for an **i18n foundation to be built now** (not fully translated content, but the underlying plumbing), specifically so it doesn't have to be retrofitted once the number of pages grows. See `docs/ARCHITECTURE.md` §12 and `docs/PRD.md` §9.24 for the concrete shape (locale context/provider, cookie persistence, English-fallback lookup, message-catalog file structure) and what was actually implemented this slice vs. deferred.

**Why:** The same reasoning as any cross-cutting infrastructure decision (auth, audit logging) - retrofitting locale-awareness into markup, routing, and data models after dozens of pages exist is materially more expensive than building the seam now and filling in translations incrementally per the user's own framing ("full translations may be completed gradually as each feature is built").

**How to apply:**
- One product record per product, always - translations are a side table keyed by `product_id` + `locale`, never per-locale duplicate product rows or per-locale columns on `product` (reaffirms the entry above; this is now non-negotiable, not just a schema-shape preference).
- English is the unconditional fallback at every lookup site - a missing translation renders the English string, never a blank or a raw translation key.
- Seller-submitted or AI-generated translations are never auto-published - they enter the same kind of admin-approval queue as product content itself (see `docs/PRD.md` §9.19 moderation, §9.24).
- Prices stay USD-only for this release regardless of locale - locale changes display language, not currency/units.
- Non-Latin scripts (Amharic and Tigrinya specifically use Ge'ez script) must render correctly everywhere text flows: UI, database storage, emails, and search - this is a UTF-8-throughout requirement (Postgres already defaults to UTF-8; verify email templates and any future search-index configuration don't silently assume Latin-1/ASCII).
- Layouts must not assume English-length strings - a button/menu/form built to fit an English label must not break when the same slot holds a longer Amharic or Spanish translation; this is a design-system requirement (`docs/DESIGN-SYSTEM.md` §12), not just a translation-content concern.

## Every session-scoped Next.js page exports `dynamic = "force-dynamic"`

**Date:** during the product-catalog vertical slice, while writing its E2E tests.

**Decision:** Every page across all three frontends that renders data scoped to the caller's session (seller product list/detail/preview, seller dashboard, admin product list/detail, admin application list/detail) now has an explicit `export const dynamic = "force-dynamic"`.

**Why:** An E2E test ("seller A is blocked from editing seller B's product") initially failed with the product detail page returning HTTP 200 and seller B's private draft content for a request made under seller A's session. Investigated as a potential real cross-tenant data leak (the highest-severity class of bug for this platform per `docs/SECURITY.md` §1) before doing anything else. Three independent checks - an isolated Node script hitting the backend directly with fresh tokens, the full backend integration-test suite, and the E2E test itself once given an explicit wait for the login redirect to complete - all confirmed the *backend* authorization was correct throughout; the failure was a Playwright test race (asserting on the target page before the login Server Action's cookie swap had fully completed), not a real vulnerability. `force-dynamic` was added anyway during the investigation as defense-in-depth: even though it turned out not to be the root cause here, rendering a session-scoped page without it leaves the door open for the browser (or a future production reverse-proxy/CDN) to cache a response for a URL whose authorized content differs per caller - exactly the shape of bug this investigation was chasing.

**How to apply:** Any new page reading `cookies()` to resolve a caller's identity and then fetching data scoped to that identity should include `export const dynamic = "force-dynamic"` as a matter of course, not only when a bug prompts it. Public, non-session-scoped pages (storefront product pages, the seller-application public status page) don't need this - the same content is correct for every viewer, so caching them is fine and even desirable.

## Product-discovery slice: categories reuse Medusa's native tree, search ships as a live-query adapter with no index table

**Date:** product-discovery/categories/search/filtering vertical slice.

**Decision:** Two scope calls made while implementing this slice, both narrower than the originally-sketched design:

1. **No custom category-structure module.** Medusa's native `product-category` model already has full parent/child support (`parent_category_id`, `mpath` materialized path) and native `createProductCategoriesWorkflow`/`updateProductCategoriesWorkflow`/`deleteProductCategoriesWorkflow`. The only genuinely new thing categories needed was translations, so the only new module is `category-translation` (a `category_id` + `locale` side table, English implicit via the native `name` - same shape as the deferred `product_translation` table). Admin category CRUD composes the native category workflows as steps inside this project's own `create-category`/`update-category`/`delete-category` workflows (alongside the translation writes and the audit log), the same saga pattern as `approve-product-listing.ts`.
2. **Search v1 has no index table at all**, which is a step further than `docs/ARCHITECTURE.md` §6's original sketch (which described a Postgres tsvector/GIN-indexed table populated by `indexProduct`/`removeFromIndex` calls from event subscribers). Instead, `PostgresSearchService.searchProducts()` queries live `approved` `product_listing` rows joined against native product/variant/inventory/pricing data on every request, through Medusa's own query engine - filtering by category/vendor in Postgres, then by keyword/size/color/price/availability in application code, bounded to 500 candidate rows.

**Why:**
- For categories: building a parallel custom tree structure when Medusa already ships one battle-tested (duplicate-detection, cascade rules, cycle-safe repository methods) would have been the "unnecessary libraries/reinvention" mistake CLAUDE.md rule #10 warns against, just self-inflicted instead of a third-party dependency.
- For search: an index table is a second source of truth that can silently drift from the real approval/status data if any code path forgets to call `indexProduct`/`removeFromIndex` (a real historical class of bug in marketplace search systems - stale search results for products that are no longer live). A live-query adapter can never drift, by construction, at the cost of not scaling to a large catalog or supporting relevance ranking - both of which are exactly the triggers for swapping in a real provider (Algolia, or a ranked Postgres FTS adapter) later. The `SearchService` interface in `packages/search-contract` is what actually delivers "architecture ready for a future dedicated search provider" - the promise was about the interface boundary, not about pre-building index-maintenance machinery nothing yet needs.

**How to apply:** When a future dedicated search provider is added, write a new class implementing `SearchService` and swap it in behind `apps/backend/src/api/products/route.ts` - no caller changes. That adapter is the first code that will need `indexProduct`/`removeFromIndex`-style hooks (called from the approve/reject/update-draft workflows, the same places the old sketch envisioned event subscribers), since only then does an index exist to keep in sync.

**Pagination:** `/products` accepts and returns an opaque `cursor` string (base64-encoded offset under the hood) rather than true keyset pagination. This satisfies the "cursor-based loading" requirement from the caller's point of view (the token is opaque; nothing about it is a raw page number a client could tamper with meaningfully) while staying simple enough to implement correctly against an application-level-filtered, non-indexed result set. Revisit if/when a real search provider with native pagination support replaces the v1 adapter.

**Facets:** the `/products` response includes `facets: { sizes, colors }` reflecting every active filter *except* size/color themselves (category, brand, price, availability, keyword still apply) - so selecting one facet value never removes the other values from the dropdown, standard faceted-search behavior.

**`/brands` route (not originally speced) was added** because a real "filter by brand" UI needs a list of sellers to choose from - it returns only `{slug, name}` for sellers with at least one `approved` listing, never `vendor_id` or any other seller record field, mirroring the "brand = seller's public name" discipline already established for the single-product route.

## Two real bugs found via integration/E2E testing this slice, both fixed at the root cause

**Date:** same slice, during test-writing and verification.

**Bug 1 - test database missing a migration.** The new `category_translation` migration was generated and run against the local dev database, but an earlier attempt to also migrate the test database (`bawi_shopping_test`) used a shell `DATABASE_URL=$(grep ... .env.test)` extraction that silently picked up the wrong value, so the migration never actually ran there. The first integration test that exercised `GET /admin/categories` (which joins in `category_translation`) failed with a real Postgres `relation "category_translation" does not exist` (`TableNotFoundException`), not a mocked/assumed failure. Fixed by re-running `DATABASE_URL="postgresql://bawishopping@127.0.0.1:5544/bawi_shopping_test" npx medusa db:migrate` with an explicit, correct connection string, then verifying with `psql ... \dt`.

**Bug 2 - `listProductCategories({ id })` with no explicit `select` silently returns a near-empty object.** The admin `GET /admin/categories/:id` route (and the existence-check reads inside `PUT`/`DELETE`) called `productModuleService.listProductCategories({ id: req.params.id })` with only a filter, no `select`/config argument - Medusa's list method in this shape returns objects with only `id` populated (and any relation-graph defaults), silently dropping `name`, `handle`, `parent_category_id`, `is_active` (all `undefined`, so `JSON.stringify` dropped them from the API response entirely rather than erroring). This was invisible in the integration tests (which mostly assert on POST/PUT *inputs* and re-fetch via the list route, which *does* pass an explicit `select` and worked correctly) and only surfaced through a real browser E2E run: editing a child category's translations pre-selected "No parent (top-level)" in the parent dropdown (because `initialValues.parent_category_id` was `undefined`), and saving would have silently detached the category from its parent by sending an explicit `parent_category_id: null` - a real data-loss bug that unit/integration tests alone did not catch. Fixed by adding the same explicit `select: ["id", "name", "handle", "parent_category_id", "is_active"]` used by the working list route to all three call sites in `apps/backend/src/api/admin/categories/[id]/route.ts`, then re-verified live in a browser (create parent → create child → edit child's translation → confirm the parent link and the translation both persisted correctly) before re-running the full E2E suite.

**Why this is worth recording:** neither bug was caught by unit tests (both are integration-boundary issues - a real Postgres schema state, and a real Medusa ORM query-shape default) and the second was only caught by *watching real rendered UI state in a browser*, not by asserting on API JSON shape alone. Backend integration tests proved the API *inputs* worked; they didn't prove the admin *UI* read its own API responses correctly. This is why this slice's verification included a live `Claude_Browser` walkthrough of the admin category edit flow in addition to Playwright E2E, not just automated test suites - and it's a concrete argument for keeping `select` explicit on every `listX` call that feeds a UI form's pre-filled state, not just on the ones already known to need it.

**How to apply:** Never call a Medusa `listX`/`retrieveX` method without an explicit `select` (or `fields`) when the result will be used to populate more than an existence check - relying on "no select means all fields" is not a safe assumption in this Medusa version. When adding a new migration, always verify it actually ran against the test database with a direct `psql \dt` check (or equivalent), not just a "Migrations completed" log line from a command whose `DATABASE_URL` was assembled indirectly (shell substitution, `.env` parsing) rather than passed literally.

## Merchant-of-record: RESOLVED — Bawi Shopping is the merchant of record

**Date:** start of the payments/checkout build-out, immediately before Phase 1 (Stripe Connect seller onboarding).

**Decision:** Every previously-"unresolved" mention of merchant-of-record in this codebase's documentation (`CLAUDE.md`, `docs/PRD.md`, `docs/SECURITY.md`, `docs/IMPLEMENTATION-PLAN.md`) is now **finalized, not open**: **Bawi Shopping is the merchant of record for every transaction.** Customers purchase from Bawi Shopping, not directly from an individual vendor. Bawi controls the customer relationship, payment, receipts, customer service, delivery tracking, returns, refunds, disputes, and seller payment. This confirms, rather than changes, the payment *mechanics* already sketched in `docs/PAYMENTS.md` (Separate Charges and Transfers, platform Stripe account as merchant of record) - what was missing was the explicit business/legal sign-off that those mechanics were the final answer, not a placeholder assumption. Nothing about the technical design changes as a result; every doc that said "must be finalized before payments are implemented" can now proceed.

**Payment architecture, confirmed as final (not a re-derivation - see `docs/PAYMENTS.md` for full mechanics):**
1. Customer charges are created on Bawi's Stripe **platform** account (`PaymentIntent`), never on a seller's connected account.
2. Sellers onboard as Stripe Connect **Express** connected accounts (KYC/bank details hosted entirely by Stripe - see §2 below).
3. **Separate Charges and Transfers**, not Destination Charges - required because one cart can span multiple vendors and the customer pays exactly once regardless of how many sellers are represented.
4. **No direct charges.** A vendor must never appear as the Stripe-visible, customer-facing merchant on any receipt, statement descriptor, or Payment Element.
5. Bawi bears Stripe fees, refund/dispute/chargeback liability, negative-balance risk, and reconciliation - a seller's connected account is a payout destination, not a second merchant of record.
6. Seller Transfers are created separately from, and always after, the customer charge - never atomically combined with it.
7. A Transfer is never created until the configured fulfillment/delivery/risk checks for that vendor order have passed (mechanics land with Phase 7 - Commission ledger, seller transfers, and payout reporting).
8. Transfer timing/holding-period is a **configurable business value** (see the business-configuration entry below), not a hardcoded constant - required so it can be tuned per environment and per future policy change without a code deploy.
9. Refunds and disputes must be able to reverse a Transfer and adjust the seller's ledger - designed in from the start at Phase 7/8, not retrofitted.
10. Every Stripe payment, transfer, refund, dispute, and webhook operation is idempotent by provider event/object ID - same discipline already established for `seller-application`/`product-listing` approval workflows, extended to money movement.
11. **Stripe test mode only, until an explicit, separate production-launch approval.** No code path may switch to live Stripe keys automatically - see the feature-flag entry below (`live_payments_enabled`, hardcoded default `false`, never flipped by a migration/seed/config default).
12. **Bawi's own database never stores bank account numbers, identity documents, tax IDs, or a full Stripe account object.** The `seller` table gains exactly one Stripe reference (`stripe_account_id`, an opaque ID string) plus three booleans (`stripe_charges_enabled`, `stripe_payouts_enabled`, `stripe_details_submitted`) derived from `account.updated` webhooks - never the raw webhook payload, never anything Stripe classifies as KYC/financial-instrument data.

**Privacy requirements, confirmed as final:**
- Vendor identity stays private from customers; customer identity and delivery address stay private from vendors (reaffirms CLAUDE.md rule #12 and `docs/SECURITY.md` §11 - not a new rule, a confirmation it now also governs the payments/checkout build-out).
- **Product brand and vendor identity are separate concepts**, made explicit for the first time here: a normal product brand (e.g., a manufacturer/label name on the product itself) may be shown publicly same as today. A *vendor's own store name or vendor-owned brand* is different - it may only be published when Bawi admin explicitly approves it for public display (a new `seller.public_brand_display_approved` flag, admin-controlled, defaults `false`; see `docs/DATABASE.md`). Until approved, a vendor-owned brand is treated with the same privacy tier as the vendor's identity generally.
- Never expose `vendor_id`, Stripe connected-account IDs, private SKUs, pickup addresses, seller emails, or seller phone numbers through the storefront - reaffirms and extends the existing "never expose vendor_id or private SKU" discipline already enforced on the product/discovery routes to now explicitly cover Stripe account IDs as equally sensitive.
- Seller-facing APIs must never return customer names, delivery addresses, phone numbers, emails, or payment information - reaffirms `docs/SECURITY.md` §11's existing rule, now explicitly extended to payment information.
- Courier access is limited to the courier's one assigned delivery and is logged (mechanics land with Phase 6).
- All sensitive data access and status changes require audit records - reaffirms CLAUDE.md rule #6, now explicitly extended to Stripe account status changes and business-configuration edits (see below).

**Why now, why this answer:** the business decided Bawi is the merchant of record (not each vendor) - an Amazon-Marketplace-style model, consistent with everything already built (Bawi already controls listings, pricing, customer service framing, and private fulfillment per the earlier private-fulfillment decision). This was the one remaining fact needed to unblock Phase 4 (checkout/payments) in `docs/IMPLEMENTATION-PLAN.md`, and it resolves in the direction every other doc already assumed as the *likely* answer while explicitly declining to build against it as fact - so this decision changes zero code by itself, only doc language and what's now permitted to be built.

**How to apply:** Every "explicitly unresolved" / "must be finalized before payments" sentence across `CLAUDE.md`, `docs/PRD.md`, `docs/SECURITY.md`, and `docs/IMPLEMENTATION-PLAN.md` is updated in this same change to say "resolved - Bawi is merchant of record" and point here. No future doc or code should re-litigate this as open.

## Business configuration is centralized, versioned, and audit-logged - development/staging defaults are explicit mocks, not silent placeholders

**Date:** same window, immediately before Phase 1 implementation began.

**Decision:** Rather than hardcoding commission rate, transfer-hold period, return window, seller prep deadline, shipping fee, free-shipping threshold, service area, and similar business inputs into checkout/order/fulfillment logic as they're built phase by phase, a new custom module (`business-config`) is a **generic category/key/value configuration store**, seeded now with explicit development/staging default values, each one flagged `is_placeholder: true` where it represents a real business/legal/operational decision still pending final approval. A parallel, fixed set of **feature flags** (`live_payments_enabled`, `real_transfers_enabled`, `real_payouts_enabled`, `real_refunds_enabled`, `real_tax_calculation_enabled`, `real_email_enabled`, `real_sms_enabled`, `real_courier_booking_enabled`, `promotional_codes_enabled`) all default to `false` and gate every code path that would otherwise move real money, send a real communication, or book a real courier.

**Seeded development/staging defaults (all `is_placeholder: true` unless noted):**
- Marketplace commission: 15% (1500 basis points)
- Seller transfer hold: 7 days after confirmed delivery
- Customer return window: 14 days after delivery
- Seller preparation deadline: 48 hours
- Initial service area: Dallas-Fort Worth, Texas
- Standard shipping fee: $6.99 (690 cents)
- Free-shipping threshold: $75 (7500 cents) per order
- Cancellation policy: allowed until the seller marks the fulfillment order "preparing"
- Return shipping: customer pays, unless the product is defective/damaged/incorrect/materially different from the listing
- Support email: `support@example.bawishopping.com` (placeholder domain, not a real mailbox)
- Support phone: a clearly fake test value, never a real number
- Tax provider: mock tax-calculation adapter (no real tax jurisdiction logic yet)
- Courier provider: internal mock courier adapter (no real courier integration yet)
- Currency: USD (not a placeholder - a genuine v1 scope decision, see `docs/PAYMENTS.md`)
- Promotional codes: disabled for v1 testing (not a placeholder - a genuine scope decision, tracked by the `promotional_codes_enabled` feature flag)
- Vendor-owned store name/brand: hidden by default, requires explicit Bawi admin approval to display publicly (not a placeholder - the confirmed privacy rule itself, see above)

**Why:** four reasons, in order of importance. (1) None of these values are engineering defaults to guess at - they're real business/legal/operational inputs this project has repeatedly (and correctly) refused to invent (see the merchant-of-record entry above, and every "not an engineering default to guess at" note already in `docs/IMPLEMENTATION-PLAN.md`). Centralizing them makes every one individually visible, individually replaceable, and impossible to silently forget. (2) Snapshotting: rule - every order, at creation time, copies the commission rate/shipping fee/return-window value *in effect at that moment* onto the order itself (a later config change must never retroactively alter a past order's economics) - this requires the values to live somewhere versioned and readable at order-creation time, which a scattered set of hardcoded constants cannot provide. (3) Feature-flagging every real-money/real-communication code path is the only way to let phases 2-11 be built and fully tested end-to-end (including Playwright E2E) without any risk of an accidental real Stripe transfer, real payout, real email, or real SMS - the flags are the actual technical mechanism, not just documentation, that make "use mock adapters, continue building" safe. (4) A single, queryable "is this placeholder still in place" surface is what makes a production-readiness check (see below) possible at all.

**How to apply:**
- Money values are integer cents; rates are basis-points integers - reaffirms `docs/DATABASE.md` §1's existing monetary-representation rule, now explicit for business-config values too.
- Every write to a `business_config_entry` is audit-logged (actor, before/after value) via the same `audit-log` module already used for seller-application/category actions - no exception.
- A new `apps/backend/src/scripts/check-production-readiness.ts` (`medusa exec` script) lists every `is_placeholder: true` row still at its seeded default, and every `real_*`/`live_payments_enabled` feature flag still `false`, as a single readable report; it exits non-zero when any placeholder remains, so it can gate a release process later even though no CI pipeline runs it automatically yet (see `docs/IMPLEMENTATION-PLAN.md`).
- Mock adapters (tax, courier, email, SMS) are only built as each consuming phase actually lands (checkout/Phase 3 for tax, Phase 6 for courier, Phase 9 for email/SMS) - the category/key rows and feature flags exist now so those phases have a place to read from and a flag to gate on, but an adapter with no caller yet is not built ahead of need (reaffirms CLAUDE.md rule #10, "no unnecessary libraries/abstractions built ahead of a real consumer").
- Before real production launch, an operator must explicitly replace and approve: commission percentage, seller transfer schedule, return policy, shipping fees, service area, tax provider, courier provider, customer-support details, legal policies, live Stripe credentials, and production email/SMS providers - none of these flip automatically, and `live_payments_enabled`/`real_*` flags are never set to `true` by a migration, seed script, or environment-variable default.

## Multi-vendor cart: native Medusa cart module + custom server-side validation layer, guest identity via header (not a backend-set cookie)

**Date:** same window, Phase 2 (multi-vendor shopping cart).

**Decision:** Cart persistence uses Medusa's native `cart` module entirely unmodified (no new tables) - `currency_code: "usd"` only, no region/sales-channel, since pricing is flat USD the same way the product-discovery slice already computes it. All marketplace-specific behavior (approval-status enforcement, vendor ownership, price/inventory re-resolution, response shaping) lives in a new `apps/backend/src/cart/` library used by custom `/store/cart/*` routes - not Medusa's native `/store/carts` REST surface, which has no concept of `product_listing` approval and would accept a client-supplied `unit_price`.

- **`resolveCartVariant()`** (`src/cart/cart-catalog.ts`) is the single source of truth for a variant's current price, live inventory, and vendor ownership, re-run on every add and on every cart read/mutation - never trusted from the request or from what's already stored on the line item. Returns `null` for any product whose `product_listing.status !== "approved"`, which is what makes draft/pending_review/rejected/archived products unreachable from the cart.
- **Vendor ownership** is stored only in a line item's internal `metadata.vendor_id` (plus `color`/`size` for display fallback) - never a first-class field, never selected into any response. `refreshAndShapeCart()` (`src/cart/cart-response.ts`) is the sole function that turns raw Medusa cart/line-item rows into the public response shape, and it never reads `metadata` back out except to resolve the (already-approval-gated) seller for the `brand` field via the same `resolvePublicBrand()` helper used elsewhere (see below).
- **Guest identity is a request header, not a cookie the backend sets.** The opaque cart id (Medusa's own cart `id`, already a ULID) travels as `x-cart-id`, forwarded by the storefront's Server Actions from an httpOnly/secure/`SameSite=Lax` cookie *it* owns (`apps/storefront/src/features/cart/constants.ts`) - mirroring the existing pattern where `CUSTOMER_SESSION_COOKIE` is entirely Next.js-managed and forwarded as an `Authorization: Bearer` header. This keeps the Medusa backend a pure API with no cookie-parsing dependency, and means every `/store/cart*` route needs only one new middleware entry: `authenticate("customer", ["bearer","session"], { allowUnauthenticated: true })`, so a single route handler serves both guest and logged-in customers without duplicating logic.
- **Mutations run through Medusa workflows**, not direct service calls from route handlers (`add-cart-item.ts`, `update-cart-item-quantity.ts`, `remove-cart-item.ts`, `clear-cart.ts`) - this project's `@medusajs/no-service-mutations-in-api-route` lint rule flags direct `cartModuleService.addLineItems()`/etc. calls from a route file, and workflows are the established pattern for that (matching `update-business-config-entry.ts`, the Stripe onboarding workflows). Add/update carry real compensation (restoring the previous quantity/price, or deleting a newly-created line item); remove/clear intentionally don't (Medusa's generated CRUD soft-deletes but exposes no restore method, and there's nothing downstream in either workflow that could fail and need a rollback).
- **Cart expiration is a business-config value, not hardcoded** (`cart` category: `cart_expiration_days` = 30, `max_quantity_per_line_item` = 10 - both `is_placeholder: false`, a genuine v1 engineering default rather than a pending business/legal decision). An expired cart is never deleted; `findActiveCart()` simply stops resolving it, and the next add-to-cart transparently starts a fresh one.
- **Guest-to-customer merge** (`src/cart/merge-guest-cart.ts`) is a plain async function, not a workflow - there's no external paid side effect and no audit-log requirement for it (unlike the actions in CLAUDE.md rule #6), so the workflow ceremony wouldn't earn its keep here. It's idempotent by construction: a guest cart already claimed by the calling customer (`guest_cart.customer_id === customerId`) short-circuits with no further writes; a cart claimed by a *different* customer is ignored entirely (never merged); merging into an existing customer cart sums quantities per `variant_id` and caps to live inventory/the max, then retires the guest cart by claiming it under the customer (which is also what makes a second call against the same `guest_cart_id` resolve as "already merged" rather than double-adding).
- **A pre-existing brand-visibility gap was fixed in the same change, not deferred:** `GET /products/[code]` and the Postgres search adapter both returned `seller.name` directly as `brand`, ignoring the `public_brand_display_approved` flag added in the Stripe onboarding slice (that slice added the column but never wired a consumer). Since this phase's own spec requires cart items to "follow the existing Bawi approval rules" for brand, and cart pulls from the same product data, a shared `resolvePublicBrand()` helper (`apps/backend/src/modules/seller/public-brand.ts`) was added and wired into all three call sites - a vendor's own store name now only appears when Bawi has approved it; otherwise a generic `"Bawi Shopping Seller"` label is shown. The `/brands` filter endpoint has the same underlying gap but was deliberately **not** touched here - fixing it well requires deciding how an unapproved seller should behave in a *filter list* (exclude entirely vs. bucket under a generic "Other" entry), which is a product decision, not a one-line display substitution; flagged as a separate follow-up task rather than expanded into this phase.
- **Storefront customer login was added in this same change**, not deferred: the user-registration slice built `loginCustomer()` in `medusa-auth-client.ts` and an auto-login-after-register flow, but never a standalone login page - meaning "a guest registers **or logs in** and the cart persists" (an explicit acceptance criterion this phase) had no second path to exercise. `apps/storefront/src/app/(auth)/login` was added, and the merge call was wired into both the login and register Server Actions identically, right after the session cookie is set and before any redirect. A merge failure is swallowed (best-effort) in both flows - a guest-cart merge hiccup must never block a customer from completing login/registration.

**Why:** the architecture keeps "what Medusa already does well" (line-item CRUD, quantity/price fields, soft-delete) and "what's marketplace-specific" (approval gating, vendor privacy, multi-vendor response shaping) in clean separate layers, so a later checkout phase can reuse `resolveCartVariant()`/`refreshAndShapeCart()`'s re-validation logic directly instead of re-deriving it. The header-based guest identity (vs. a cookie the Medusa backend itself sets) keeps every session-token concern - cookie name, httpOnly/secure flags, forwarding - in exactly one place (the Next.js app), consistent with how customer auth already works, rather than introducing a second, inconsistent cookie-ownership model.

**How to apply:**
- Any future route that mutates a cart line item must go through a workflow (see the lint rule above), not call `cartModuleService` mutation methods directly from the route handler.
- Any future code that needs "is this variant currently purchasable, and at what price" must call `resolveCartVariant()` rather than re-deriving it - it's already the schema-correct, approval-gated source of truth product-detail and search both also (should) use.
- Checkout (next phase) re-validates at submit time using the same re-resolution approach cart already applies on every read - not a new, separate "checkout-time validation" concept.
- The `/brands` endpoint's brand-visibility gap remains open and is tracked as a follow-up, not silently accepted as fixed.

## Cart quality audit: guest-cart-merge concurrency fix, N+1 batching, error-handling consistency, accessibility fixes

**Date:** same window, immediately after Phase 2 shipped - a requested pre-Phase-3 audit of the entire cart slice.

**Decision / findings:** Six real issues were found and fixed; two lower-severity items were found and deliberately left as documented residual risk rather than over-engineered. No unnecessary duplication of Medusa functionality was found - the module map (`docs/DECISIONS.md`'s cart entry above) already draws the native-vs-custom line correctly.

**Fixed:**
1. **Guest-cart merge was not safe under true concurrency**, only sequential replay. `cartModuleService.updateCarts(selector, data)` is a `list()`-then-`update()`-by-id under the hood (confirmed by reading `@medusajs/cart`'s service source), not an atomic conditional `UPDATE ... WHERE`, so two simultaneous merge calls for the same guest cart could both pass the "not yet claimed" check and both proceed to copy line items, duplicating them. Fixed with a new `cart-merge` module (`CartMergeModuleService.claim()`, unique-index `INSERT`, same pattern as `WebhookEventModuleService.markProcessed`) that atomically claims the guest cart id *before* any merge work runs - only one concurrent caller's `INSERT` can succeed. Verified with a new integration test that fires two merge requests via `Promise.all` and asserts no duplicate.
2. **A second, subtler bug in the same code path:** the merge-into-an-existing-customer-cart branch used to attribute the drained guest cart to the customer (`customer_id` set) as its last step. Since `findActiveCart()` picks a customer's cart by "most recently updated," and that final write landed *after* the real cart's own items were written, the now-empty former guest cart could look more recently updated than the real one - the very next `GET /store/cart` could resolve to the wrong (empty) cart. Fixed by simply not attributing that drained cart to the customer at all in this branch (the claim table already makes it permanently non-reusable; leaving `customer_id` null is safe - at worst a stale cookie resolves to a harmless empty cart). Verified with a new integration test that merges into an existing cart and re-fetches immediately after.
3. **N+1 query pattern**: `refreshAndShapeCart()` (every cart read/mutation) and `mergeGuestCartIntoCustomerCart()` both looped `resolveCartVariant()` per line item - 2 sequential DB round-trips per item. Fixed with a new `resolveCartVariants()` batched form (one `query.graph` call for every variant id, one `listProductListings` call for every distinct product id); `resolveCartVariant()` (singular) is now a one-line wrapper over it. Price-drift writes and merge's new-line-item/quantity-update writes were also batched into single array-form calls instead of one write per item.
4. **Error-handling inconsistency**: every other route in this codebase manually catches and shapes errors as `res.status(code).json({ message })` (confirmed by grepping the whole `src/api` tree) rather than relying on an uncaught `throw new MedusaError(...)` reaching Medusa's default handler - even the Stripe webhook route explicitly catches and reshapes a MedusaError-throwing call rather than letting it propagate. The four cart routes were the only ones using the throw-based style; refactored to match the established manual-catch convention. No behavior change (status codes and message text are identical - confirmed no test asserted on the delivery mechanism).
5. **Test harness leak**: `medusa develop` spawns a `cli.js start --types` type-watcher sub-process that doesn't listen on any port (so the harness's existing port-based cleanup never catches it) and was observed to survive a `SIGTERM` to its process group. Across a long session running many integration-test invocations, these accumulated (five were found simultaneously) until one test run's Medusa server crashed outright mid-suite from resource exhaustion, taking down every test after that point with generic `fetch failed` errors that gave no indication anything was actually wrong with the cart code. Fixed in `integration-tests/http/test-server.js`: `stopTestServer()` now sends `SIGKILL` (not `SIGTERM`) to the process group, and both `startTestServer()`/`stopTestServer()` additionally run a targeted `pkill -9 -f "medusajs/cli/cli.js start --types"` as defense in depth. The harness now also persists the child server's stdout/stderr to a fixed temp-file path (previously buffered in memory only, for the "did it start" check, and otherwise unrecoverable) so a future crash is diagnosable without re-running blind.
6. **Two accessibility gaps**: the cart page's per-item "Update"/"Remove" buttons had generic accessible names with no item-specific context - ambiguous for a screen-reader user tabbing through a multi-item cart (fixed with `aria-label` incorporating the item title; component test updated to match the new accessible name). The header cart icon's tappable area was only the icon's own 20x20px box, below the WCAG-recommended ~44x44px minimum touch target (fixed with padding + a compensating negative margin).

**Deliberately left as documented residual risk, not fixed:**
- **Concurrent add-to-cart quantity increments for the same variant/cart can lose an update** (last-write-wins: both requests read the same starting quantity, both compute and `SET` the same new absolute total, rather than a true atomic increment). No `version`/optimistic-lock column exists on Medusa's native `cart_line_item` table, and no raw-SQL atomic-increment or advisory-lock mechanism is used anywhere else in this codebase. Fixing it properly would mean dropping below the module-service abstraction this project consistently uses everywhere else, for a narrow edge case (the same user double-clicking add-to-cart for the same variant) whose worst outcome is a visibly-wrong, easily self-corrected quantity - not a security or cross-tenant issue, and not a duplicated/lost line item the way the merge race was. This is the same class of trade-off already accepted in `docs/IMPLEMENTATION-PLAN.md` for seller-application approval ("Approval idempotency has a narrow race window under true concurrent requests... a documented residual risk, not yet guarded by a DB-level lock or unique constraint").
- **The `/brands` filter endpoint's brand-visibility gap**, already flagged as a follow-up in the previous decision entry above, remains open.

**How to apply:**
- Any future guest-cart-merge-shaped problem (claim something once, safely, under real concurrency) should reach for the same unique-index-`INSERT` claim-table pattern, not `cartModuleService.updateCarts(selector, ...)` or an in-memory check-then-write.
- Any future code resolving more than one cart line item's variant at once must use `resolveCartVariants()`, not a loop over `resolveCartVariant()`.
- New backend routes should shape errors as `res.status(code).json({ message })`, matching the rest of `src/api` - not an uncaught `throw new MedusaError(...)`.

## Checkout and multi-vendor order splitting: `marketplace-order` module (not `order`), no separate `payment` module, mock tax adapter, proportional shipping/tax allocation, no guest checkout

**Date:** same window, Phase 3+4 combined ("Batch 1: Commerce Engine" per the user's 5-batch plan for the remaining phases).

**Decision / key choices:**

1. **The custom order module is named `marketplace-order` (table `marketplace_order`), not `order`.** Medusa's framework reserves the module key and entity name `Order`/`order` for its own native commerce module - even though this project deliberately doesn't use that native module (same reasoning as not using Medusa's native `payment` module, see below), attempting to `model.define("order", ...)` inside a custom module still collided with the framework's own module-link/GraphQL-schema generation during `medusa db:generate` (`Syntax Error: Unexpected Name "extend"` from a broken auto-generated link schema, plus a "No linkable key found for return_id on module order" warning). Renaming the module/table to `marketplace_order` resolved it with zero schema difference otherwise (confirmed via a second `db:generate` reporting "No changes detected" once only the DML entity's *name* changed, not its shape). **How to apply:** never name a custom module/entity `order`, `payment`, `cart`, `product`, `customer`, `user`, or any other core-module name Medusa reserves, even if the intent is to bypass Medusa's native version of that concept entirely.
2. **One module, three models - `MarketplaceOrder`, `VendorOrder`, `VendorOrderItem` - not three separate modules** (`order`, `vendor-order`, `payment`) as originally sketched in `docs/DATABASE.md`. Same one-module-multiple-models precedent as `seller`/`seller_user`: all three are created/read together inside the same checkout/capture workflows, and `MarketplaceOrder ||--|| Payment` is a strict 1:1 relationship (one PaymentIntent per order) - modeling it as a separate joined table would be pure overhead for zero benefit. Payment fields (`stripe_payment_intent_id`, `payment_status`) live directly as columns on `MarketplaceOrder`.
3. **`VendorOrder`/`VendorOrderItem` are created only *after* payment capture succeeds** (in `capture-checkout-payment.ts`'s `payment_intent.succeeded` handler), never at checkout-start - so a seller's dashboard (a later batch) can never show an order that might not end up paid. Everything needed to build them (variant/vendor/price/quantity per line) is instead frozen as `line_items_snapshot` (jsonb) on the `MarketplaceOrder` row at checkout-start, so the split never has to trust whatever the live cart looks like by the time payment actually completes (the cart could have been modified or cleared in between, and in fact *is* cleared, by this same workflow, right after the split).
4. **No guest checkout in v1** - `marketplace_order.customer_id` is `NOT NULL`, matching what `docs/DATABASE.md` already specified for the (until-now unbuilt) `order` table since the very first architecture pass. `/store/checkout*` and `/store/orders*` require `authenticate("customer", ["bearer","session"])` (no `allowUnauthenticated`), unlike cart's optional-auth middleware. A guest with items in their cart is directed to log in/register first, which already triggers the existing guest-cart-merge flow from the cart slice - no new merge logic was needed for checkout.
5. **Checkout idempotency is a client-generated key on the `MarketplaceOrder` row** (`idempotency_key`, unique), not solely Stripe's own idempotency-key mechanism (though that's also passed through to `paymentIntents.create()`). The storefront mints one UUID per checkout-page load (`crypto.randomUUID()` in the Server Component, passed as a hidden form field) rather than per form submission, so a double-click or a retried Server Action invocation naturally reuses the same key. `POST /store/checkout` checks for an existing order with that `(customer_id, idempotency_key)` pair before doing anything else, and returns the existing order/PaymentIntent state rather than creating a second one.
6. **Inventory reservation and finalization uses Medusa's native inventory module directly** (`inventoryModuleService.createReservationItems()` at checkout-start, `deleteReservationItems()` + `adjustInventory()` at capture time) - not a custom reservation concept. The single shared "Bawi Fulfillment Center" stock location (already established in the product-catalog slice) is reused as-is; per-seller stock locations remain a documented future refinement, not required for checkout to work.
7. **Shipping and tax are allocated across vendor orders proportionally by each vendor's share of the order subtotal** (`allocateProportionally()` in `capture-checkout-payment.ts`), with any rounding remainder assigned to the last vendor group so the parts always sum exactly to the order-level whole. There is no per-seller shipping/tax configuration yet - an even split by item-value share is the documented v1 approach, to be revisited once real per-seller shipping options or a real tax provider exist.
8. **"Shipping-option selection" is the existing single flat-fee-or-free calculation** (`calculateShippingEstimate()`, already built in the cart slice) shown as one line item at checkout - not a new multi-carrier/multi-option shipping module. Building a real options selector ahead of any actual carrier integration would be exactly the kind of ahead-of-need abstraction CLAUDE.md rule #10 warns against.
9. **A new mock tax adapter** (`src/tax/tax-calculator.ts`, `calculateMockTax()`) applies one flat rate (`business-config` category `tax`, key `mock_rate_basis_points`, seeded 825 = 8.25% as a plausible placeholder for the initial Dallas-Fort Worth service area, `is_placeholder: true`) uniformly regardless of the shipping address/jurisdiction - this is the "mock adapter built only when its consuming phase lands" pattern already established for tax/courier/email/SMS in the business-config decision entry above; checkout is that phase for tax. Tax is applied to the item subtotal only, not shipping - a common but not universal convention, to revisit once a real tax provider replaces this adapter.
10. **Shipping address is collected inline at checkout and snapshotted onto the order** (`marketplace_order.shipping_address`, jsonb) - not yet a reusable, saved `customer_address` record the customer can manage across orders. Saved addresses are an explicit later-batch customer-portal feature (per the user's own 5-batch plan); building that CRUD now would be ahead of need.
11. **The full 6-file backend integration suite, and the new `checkout.spec.ts` integration test specifically, could not be run to completion in this session** - the development machine was under severe memory pressure (as low as ~350MB free of 8GB) from other running applications, causing every attempt (including `checkout.spec.ts` alone) to be killed by the OS (`SIGKILL`, exit 137) before any test output was produced, confirmed not to be a code issue via the same diagnostic process used earlier in the Phase 2 cart audit. Per explicit instruction, this was not repeatedly retried; it's recorded here as a deferred, infrastructure-only gap. Unit tests, lint, typecheck, and production builds all pass; the integration test file itself is written and should be run once the machine has more available memory.

**Why:** every choice above either reuses an existing, proven pattern from earlier slices (claim-table idempotency, one-module-multiple-models, snapshot-at-creation-time, mock-adapter-on-first-real-consumer) rather than inventing a new one, or is a deliberate, explicitly-scoped simplification (flat shipping, mock tax, no guest checkout, no saved addresses) matched to what the user's own batch plan says is in scope now versus later. Splitting into vendor orders only after capture, not before, is the one choice that's load-bearing for a stated privacy/business rule (a seller should never see an order that might not get paid) rather than just convenient.

**How to apply:**
- Never name a new custom module/entity after a Medusa-reserved core-module concept (`order`, `payment`, `cart`, `product`, `customer`, `user`, ...), even when the intent is to replace/bypass that native module entirely - verify with a `db:generate` dry run before writing much code against the name.
- Any future code needing "what does this line item/vendor/order look like" after checkout has started should read from the frozen `line_items_snapshot`/vendor-order snapshot fields, never re-derive it from the live cart or a live product/pricing lookup.
- A future payouts/commission-ledger batch reads `vendor_order.commission_rate_basis_points`/`commission_amount` (already snapshotted) rather than re-resolving the rate from `business-config` at payout time.
- `checkout.spec.ts` should be re-run once the development machine has more available memory (or in CI, which isn't memory-constrained the same way) - do not treat its absence from a passing run as evidence of a code problem; the code itself passes lint, typecheck, and build.
- `integration-tests/http/test-server.js`'s persisted log (path is `os.tmpdir()/medusa-test-server.log`) is the first place to look when a long integration run dies mid-suite with generic connection-refused/fetch-failed errors.

## Private fulfillment and delivery: `fulfillment-privacy` module, unified redemption-claim table, courier portal inside `apps/admin`, code-based proof of delivery

**Date:** same window, Phase 5+6 combined ("Batch 2: Private Fulfillment and Delivery" per the user's 5-batch plan for the remaining phases).

**Decision / key choices:**

1. **New module `fulfillment-privacy`, four models: `Courier`, `PickupCode`, `TrackingCode`, `FulfillmentCodeRedemption`.** `Courier` is its own actor type (same custom-actor-type mechanism as `seller_user` - `app_metadata.courier_id`, no special medusa-config registration needed, confirmed by reading how `seller_user` already works: Medusa's generic `/auth/:actor_type/:provider` routes work for any actor type string as long as an `auth_identity` exists with `app_metadata[<actor_type>_id]` set). Couriers are provisioned directly by an Admin, not self-service - they're Bawi contractors/employees, not independent applicants like sellers - reusing the exact same activation-token pattern as `seller_user` (same "no email service yet, return the link in the admin response" stand-in).
2. **`pickup_code` and `tracking_code` are two distinct tables with identical shape but different roles**, not one shared code, per the requirement: `pickup_code` is shown to the **seller** and redeemed by the **courier** to confirm pickup; `tracking_code` is shown to the **customer** (on their order-tracking page) and redeemed by the **courier** as proof of delivery. Both are minted together, atomically, the moment a `vendor_order` transitions to `ready_for_pickup` - not lazily at pickup/delivery time - so the customer can see (and share) their delivery code well before the courier ever needs it.
3. **Single-use/replay-protection is a separate `FulfillmentCodeRedemption` claim table (unique-index `INSERT`), not an `UPDATE ... SET status = 'used' WHERE status = 'active'` conditional on the code tables themselves.** This directly reuses the finding from the Phase 2 cart audit: Medusa's generated `update<Model>s(selector, data)` is confirmed (by reading compiled source) to be a non-atomic list-then-update, not a real conditional `UPDATE`, so it cannot safely enforce "exactly one caller wins" under concurrency. The claim table is the same proven shape as `processed_webhook_event`/`cart_merge_claim`: an `INSERT` either succeeds (this caller redeemed it) or hits a unique-constraint violation (already redeemed - reject as invalid/replayed), with zero possibility of two concurrent redemption attempts both succeeding. One shared `code_type` (`pickup`/`tracking`) + `code_id` column covers both code tables rather than two near-identical claim tables, since both id spaces are globally-unique ULIDs.
4. **The courier portal is a thin route group inside `apps/admin` (`/courier/*`), not a sixth full app** - `docs/ARCHITECTURE.md` had left this explicitly undecided ("may be a thin scoped view... rather than a sixth full app, given how narrow the courier role's access is"); this batch resolves it in that direction. It has its own session cookie (`bawi_courier_session`), its own `features/courier-portal/` (auth, assignments) kept deliberately separate from `features/auth/`'s admin-`user` session code, and its own login/activation pages - a courier session and an admin `user` session are different actor types that happen to share one Next.js deployment, not one merged session model.
5. **`VendorOrder` gained `assigned_courier_id` and five lifecycle timestamps as plain columns on the existing table**, not a separate `courier_assignment` table - an admin assignment is a 1:1, in-place relationship (a vendor order has at most one *current* courier), and the timestamps (`preparing_at`/`ready_for_pickup_at`/`picked_up_at`/`out_for_delivery_at`/`delivered_at`) are exactly what the customer-tracking view and the seller/courier dashboards need to render a timeline, without a join.
6. **Three purpose-built response shapers** (`src/fulfillment/seller-fulfillment-response.ts`, `src/fulfillment/courier-assignment-response.ts`, and the existing `src/orders/order-response.ts` extended) each exclude the other parties' data **by construction** - the seller shaper never fetches the parent order's `customer_id`/`shipping_address` at all, the courier shaper never fetches order financials or the seller's real name, and the customer shaper never includes `vendor_id`, the seller's real name, or the seller-facing `pickup_code`. This is the same "build to exclude, don't filter after the fact" discipline `docs/SECURITY.md` §11 already required in writing before this slice existed.
7. **A courier never sees a code's value in advance - only what's submitted to it for verification.** The pickup code is seller-facing, the tracking/delivery code is customer-facing; the courier's own dashboard displays neither ahead of time. This is what makes the delivery code a genuine customer-controlled proof of delivery (the customer has to actually be there and hand it over) rather than the courier self-certifying completion - a deliberate design choice, not an oversight that happens to look that way.
8. **"Audit logs for sensitive access" is satisfied by auditing every courier read of an assignment's detail** (`GET /courier/assignments/:id` writes a `vendor_order.assignment_viewed` entry, actor_type `courier`), not only status-changing writes - a new, explicit requirement this batch, distinct from every earlier slice's audit-logging (which only ever logged mutations).
9. **`audit_log.actor_type` gained a fifth value, `courier`** (migration, additive `CHECK` constraint change) - couriers now perform audited actions (pickup/delivery confirmation, assignment views) and needed their own actor-type tag, same as `customer`/`seller_user`/`user`/`system`.
10. **Proof of delivery is the tracking/delivery-code confirmation itself, not photo or signature capture.** Building photo/signature capture would require file-upload wiring, object-storage integration, and a review UI this batch's scope doesn't call for; the code-based confirmation is a real, working proof-of-delivery mechanism (the same pattern major delivery apps use for a PIN-based drop-off) and is the documented v1 scope - richer capture is a future enhancement, not a gap being silently ignored.
11. **Pickup location resolution reuses the existing single shared stock location unchanged** (`getOrCreateDefaultStockLocationId`/the same "Bawi Fulfillment Center" location already established for inventory) - `shapeVendorOrderForCourier()` reads that location's own name/address at request time, so a future per-vendor-location or Bawi-sorting-hub model changes what this resolves *to*, not the response shape or the courier-facing code that reads it - exactly the flexibility `docs/ARCHITECTURE.md` §11 required in advance of this slice being built.
12. **The new `fulfillment.spec.ts` integration test (full lifecycle, pickup-code replay protection, seller/courier privacy boundaries, sensitive-access audit logging) could not be run to completion in this session** - the same development-machine memory pressure documented in Batch 1's `checkout.spec.ts` entry, confirmed again on this file specifically (identical `SIGKILL`/exit 137/zero-output signature). Not retried repeatedly per instruction; recorded here as deferred, not a code defect - the file passes lint and typecheck.

**Why:** every mechanism reused here (claim-table redemption, custom actor type via `app_metadata`, one-module-multiple-models, build-to-exclude response shaping) is a direct reapplication of a pattern already proven correct earlier in this project, rather than a new approach invented for this slice - the one genuinely new judgment call is where the courier portal lives (resolved: inside `apps/admin`, a decision `docs/ARCHITECTURE.md` had explicitly deferred) and how proof of delivery works (resolved: code-based confirmation, not media capture).

**How to apply:**
- Any future single-use/replay-protected token (of any kind, not just fulfillment codes) should reach for the same unique-index-claim-table pattern used here and in `cart-merge`/`webhook-event`, never an `UPDATE ... WHERE status = X` conditional.
- A future courier-facing feature should extend `shapeVendorOrderForCourier()`'s existing exclusion discipline, not add a new ad-hoc response shape that has to remember the same rules independently.
- `fulfillment.spec.ts` should be re-run once the development machine has more available memory (or in CI) - its absence from a passing run is not evidence of a code problem.

## Commission ledger, payouts, returns, refunds, and disputes: `seller-finance` module, derived (not stored) balance buckets, a second class of Medusa naming collision discovered

**Date:** same window, Phase 7-9 combined ("Batch 3: Marketplace Financial Operations" per the user's 5-batch plan for the remaining phases).

**Decision / key choices:**

1. **New module `seller-finance`, six models in one module: `CommissionLedgerEntry`, `Payout`, `PayoutLineItem`, `ReturnRequest`, `OrderRefund`, `Dispute`.** Same one-module-multiple-models precedent as `seller`/`seller_user` and `marketplace-order` - these six models are one coherent financial domain, not six independent concerns.
2. **A second, previously-unknown class of Medusa naming collision was discovered and fixed:** naming the refund model `Refund` (a name that is *not* on the reserved `Modules` enum module-key list already known from Batch 1's "order" collision) still failed `db:generate` with `Unable to merge GraphQL type "Refund": Field "amount" already defined with a different type` - Medusa's native order/payment modules already define their own "Refund" GraphQL entity, and schema-merging fails on any custom module reusing that exact type name, a distinct collision class from the module-key one. Fixed by renaming to `OrderRefund` (table `order_refund`). **Any future custom entity name must be checked against Medusa's native entity/type names, not just the `Modules` enum, before being used.**
3. **Ledger bucket (pending/available/paid/disputed) is derived at read time by a pure function (`deriveLedgerBucket()`, `src/finance/balance.ts`), never a stored/mutable status column** - this project has no background job scheduler or worker process (see Batch 2's payout-model reasoning, reaffirmed here), so a stored status would silently go stale the moment its `available_at` passed without a job to flip it. Order of checks matters and is deliberate: `paid_at` wins over everything (money already moved, even if later disputed), `disputed_at` wins over pending/available (freezes payout eligibility), `available_at <= now` is the only time-dependent check.
4. **Seller balance math: `net_amount = subtotal_amount - commission_amount`, deliberately excluding shipping and tax.** Bawi operates fulfillment/delivery itself and is the merchant of record for tax purposes (see the merchant-of-record decision) - shipping and tax are Bawi's own revenue/pass-through, never part of what a seller is owed. This is a new, explicit v1 business-logic decision, not inherited from an earlier slice.
5. **Transfer-hold period is snapshotted onto the ledger entry at capture time** (`transfer_hold_days_snapshot`, read from `business-config` category `transfer_timing` once, at the same point `commission_rate_basis_points`/`commission_amount` are snapshotted onto `VendorOrder`) - the same snapshotting principle applied consistently since Batch 1, so a later change to the platform's hold-period default never retroactively moves money for an order already in flight.
6. **Payout batches are an explicit admin action (`POST /admin/finance/payouts`), never automatic** - reaffirms Batch 2's "no real background scheduler" finding; "reconciliation" in this codebase is a manual admin-triggered re-fetch of Stripe Transfer state, not a cron sweep. A batch is idempotent by construction: its Stripe idempotency key is derived from the exact sorted set of ledger-entry ids being paid, and `PayoutLineItem.commission_ledger_entry_id` is a **unique** column, so a ledger entry can be claimed by at most one payout ever - re-running a batch after a partial success can never double-pay an entry.
7. **Refund/commission-reversal math is a pure function** (`calculateRefund()`, `src/finance/refund-calculation.ts`): the refund amount is always server-computed from the item's own stored `line_total_amount` (capped there, defaulting to a full refund), never a client-supplied figure; the commission reversal is proportional to the refunded ratio of the item, round-half-up (the same rounding rule as `resolveCommission()` since Batch 1).
8. **Inventory restock on an approved return depends on the return reason: damaged/defective are never restocked (the item is presumed unsellable); incorrect-shipment and customer-remorse are restocked (the item is presumably still sellable).** A new, explicit v1 policy decision, not a default Medusa behavior.
9. **A `refund_reversal` ledger entry's `available_at` is set to "now", never a fresh hold period** - per the reasoning that a reversal nets immediately against whichever bucket its original entry already sits in (pending, available, or even already-paid, in which case the seller's next payout batch simply pays a smaller net amount).
10. **A pre-preparation cancellation (`cancel-vendor-order.ts`) produces an `OrderRefund` row with `return_request_id: null`** - there is no `ReturnRequest` behind a cancellation, only behind a post-delivery return. This required making `OrderRefund.return_request_id` nullable (a second, small migration) - Postgres unique constraints don't count `NULL` against each other, so "at most one refund per return request" is still enforced for the rows that do have one.
11. **A Stripe dispute (`charge.dispute.created`/`charge.dispute.closed`) is recorded against the whole marketplace order, not per-vendor** - the customer-facing charge is one PaymentIntent for the entire cart (see Batch 1's checkout design), so a dispute can span every vendor_order under an order. `Dispute.vendor_order_id` is only set when exactly one vendor_order exists on the order; every affected vendor_order's ledger entry is frozen (`disputed_at` set) regardless, since that's what actually blocks payout. A **lost** dispute leaves `disputed_at` set permanently (no auto-reversal ledger entry exists for a lost dispute in v1 - surfaced for manual admin review, the same "best-effort, surfaced for manual reconciliation" class of accepted residual risk as an approved-return's Stripe refund/restock not being auto-reversed on a later step failure).
12. **Return approval/denial is a seller action** (`POST /seller/returns/:id/approve|deny`), matching the "seller manages their own vendor_orders" pattern from fulfillment; the admin financial dashboard has read-only oversight into every seller's returns and disputes (`/admin/finance/returns`, `/admin/finance/disputes`) for support purposes, not a duplicate approval path.
13. **A third class of Medusa workflow bug was found and fixed: nesting a `when(...).then(...)` block inside another `when(...).then(...)` callback fails at workflow-definition time** (`Cannot read properties of undefined (reading 'steps')`, thrown deep inside `@medusajs/workflows-sdk`'s composer) - caught by the very first attempt at running the new `seller-finance.spec.ts` integration test (a real bug, not the development machine's memory pressure). `apply-stripe-dispute-webhook.ts` originally nested a `charge.dispute.created`/`charge.dispute.closed` branch-selection `when()` inside an outer `claimed` `when()`; fixed by flattening to two **sibling** top-level `when()` blocks, each gated on the combined condition (`claimed && <event-type>`) instead of nesting. **Any future workflow needing more than one conditional branch should use sibling `when()` calls with combined conditions, never nest one inside another's `.then()` callback.**
14. **The new `seller-finance.spec.ts` integration test (commission ledger creation, payout batch, return approval/denial, cancellation, dispute webhook, tenant isolation) could not be run to completion in this session, even after the bug above was fixed** - the same development-machine memory pressure documented in Batch 1's `checkout.spec.ts` and Batch 2's `fulfillment.spec.ts` entries (the re-run process sat for minutes producing zero output before being terminated, a different signature from the bug above, which failed fast with a clear stack trace). **Confirmed genuinely memory-related, not another latent bug**: a later direct run (started in Batch 4, redirected to a file instead of piped through `tail`) exited with code 137 (SIGKILL) - the exact signature already documented for the other two deferred integration-test files. Not retried a third time per instruction; recorded here as deferred, not a code defect - the file passes lint and typecheck.
15. **A fourth class of Medusa workflow bug was found and fixed, in Batch 4, in this same `apply-stripe-dispute-webhook.ts` file**: invoking the *same* `createStep`-produced step at two different call sites within one `createWorkflow` composition fails at definition time (`Step <id> is already defined in workflow`) - caught not by the integration test (masked by the memory-pressure SIGKILL above) but by `npx medusa db:migrate`, which loads every workflow file as part of booting its container and surfaced the error immediately. The dispute-created and dispute-closed branches both called one shared `recordDisputeAuditLogStep`; fixed by splitting it into two distinct steps (`recordDisputeOpenedAuditLogStep`/`recordDisputeClosedAuditLogStep`, each with its own step id) that share a plain async helper function for the actual audit-log write. **A Medusa step is a compile-time graph node, not a reusable function - never call the same `createStep` result from two different places in one workflow; give each call site its own step, sharing logic via a plain function if needed.** This also means `db:migrate` (or any command that loads all workflow files) is a meaningful, cheap smoke test for workflow-definition errors independent of a full integration-test run - worth running after any workflow change even when the integration suite itself can't complete on this machine.

**Why:** the financial domain is the highest-stakes surface built so far (real (test-mode) money movement, refund calculation, dispute handling) - every design choice here either reuses a pattern this project already proved correct (claim-table idempotency, snapshotting, derived-not-stored state, build-to-exclude response shaping) or is a new, explicitly-reasoned business decision (seller balance excludes shipping/tax, restock-by-reason policy, lost-dispute residual risk) rather than an accidental default.

**How to apply:**
- Before naming any future custom DML model, grep both the compiled `Modules` enum (module-key collisions) **and** Medusa's native GraphQL type names (entity-name collisions) - this batch is the second time a Medusa naming collision has silently broken `db:generate`, and it will not be the last unless both are checked up front.
- Any new time-dependent status (subscription tiers, promotional windows, etc.) should default to the same derive-at-read-time pattern as `deriveLedgerBucket()` unless/until this project actually gains a background job scheduler - a stored status column is a silent-staleness bug waiting to happen without one.
- A future automated payout/reconciliation job (once a scheduler exists) should preserve the existing idempotency guarantees (`PayoutLineItem.commission_ledger_entry_id` unique, sorted-id-set idempotency keys) rather than introducing a new claim mechanism.
- Any future workflow with more than one conditional branch must use sibling top-level `when()` calls (combined conditions), never nest a `when().then()` inside another one's callback - this batch is the first time this project's workflows needed two independent conditional branches in one workflow, and the nested form fails at definition time, not at test time, so it will surface immediately if repeated.
- Never call the same `createStep`-produced step at more than one call site within a single `createWorkflow` body - give each call site its own step (sharing an underlying plain async function if the logic is identical), or Medusa's orchestrator rejects the workflow at definition time with "already defined in workflow."
- After any workflow file change, run `npx medusa db:migrate` (or any command that boots the full module/workflow container) even before the integration suite - it loads every workflow definition and will immediately surface a definition-time error like the two found this session, independent of whether the integration tests themselves can complete on this machine.
- `seller-finance.spec.ts` should be re-run once the development machine has more available memory (or in CI) - its absence from a passing run is not evidence of a code problem.

## Notifications and account completion: native `notification` module + a thin custom inbox, native customer-address/admin-invite reuse, seller-staff invites via the existing activation-token pattern

**Date:** same window, Phase 9-10 combined ("Batch 4: Notifications and Complete Portals" per the user's 5-batch plan for the remaining phases).

**Decision / key choices:**

1. **Notifications send through Medusa's own native `notification` module (the `notification-local` provider - console/logger only) rather than a fully custom send mechanic.** `docs/ARCHITECTURE.md` had already flagged this as the intended approach before this batch was built. Registered in `medusa-config.ts` as `{ resolve: "@medusajs/medusa/notification", options: { providers: [{ resolve: "@medusajs/notification-local", id: "local", options: { channels: ["email"] } }] } }` - swapping to `@medusajs/notification-sendgrid` (or another real provider) for production is a config change, not a rewrite.
2. **A second, small custom module (`notification_inbox`, one model: `NotificationInboxEntry`) sits alongside the native one**, because the native module has no receiver-scoped store/seller API (only `GET /admin/notifications`, and even that has no `receiver_id` filter exposed) and no read/unread state - it stores and sends, but can't serve an in-app "notification center." `notification_inbox_entry.notification_id` is unique, so a repeat of the native module's own idempotency (keyed on `idempotency_key`, e.g. `order_confirmation:${orderId}`) never produces a duplicate inbox row either.
3. **`src/notifications/record-notification.ts`'s `recordNotification()` is a plain async function called from inside workflow steps, not a step itself** - it has no meaningful compensation (an already-sent email can't be unsent), matching this project's precedent for other non-reversible side effects (audit-log writes, Stripe refunds/transfers). It's called from a small step added to each of eight existing workflows: `capture-checkout-payment` (order confirmation), `start-vendor-order-delivery` (shipment update), `confirm-vendor-order-delivery` (delivery confirmation), `approve-return-request`/`deny-return-request` (return status changed), `cancel-vendor-order` (refund processed), `create-payout-batch` (payout sent), `approve-seller-application`/`reject-seller-application` (application approved/rejected).
4. **Templates are hand-written TS functions (`src/notifications/templates.ts`), not a DB-backed template table** - there's no content-authoring UI planned for this batch and no localization requirement for transactional email (unlike UI copy), so a function per event type is the simplest thing that actually works, matching the mock-tax-adapter precedent ("as complex as its first real caller needs, not more").
5. **A rejected seller application's notification has no `recipientType`/`recipientId`** (both made optional on `RecordNotificationInput`) - a rejected application never creates a `seller_user`, so there's no in-app account to index the inbox entry against; the email still sends, there's just no inbox row, since nothing could ever query it.
6. **Saved addresses (storefront `/account`) and admin user management (admin `/team`) needed zero new backend code** - both are Medusa native functionality already: `GET/POST/DELETE /store/customers/me/addresses` (customer_address) and `GET/POST/DELETE /admin/users` + the full `/admin/invites` create/accept/list/delete surface. This batch is frontend-only for those two pieces, calling the native routes directly from server-only client functions, the same layering discipline as everywhere else in this project (custom only where Medusa has no native equivalent).
7. **Admin-invite acceptance mirrors the exact two-step exchange already used for customer registration**: `POST /auth/user/emailpass/register` (creates the auth identity, returns a registration-scoped bearer token) then `POST /admin/invites/accept?token=<invite_token>` with that bearer token finalizes the `Invite` → `User` conversion. No new backend code needed here either - `apps/admin/src/features/team/services/accept-invite-client.ts` is a pure two-fetch client function. Since there's still no email service, the invite's own `token` field is shown directly in the admin `/team` UI as a copyable activation link - the same "no email yet, show the link in the UI" stand-in used for seller/courier activation.
8. **Seller staff invites (seller-portal `/staff`) reuse the exact same activation-token mechanism as seller-application approval and courier provisioning** (`generateActivationToken()`/`ACTIVATION_TOKEN_TTL_MS` from `seller-application/utils.ts`, imported cross-module since it's a plain utility, not a service) - a new `SellerUser` row is created with `role` one of `catalog_manager|order_fulfiller|analyst` (never `owner` from this flow), and activates via the existing generic `/seller-activation/complete` route, unchanged. Only the seller's own `owner` can invite or remove staff; the owner account itself can never be removed through this route - a seller must always have exactly one owner, and ownership transfer (if ever needed) is a deliberate, separate action, not an incidental side effect of staff management.
9. **A `.env.example`/`package.json` addition**: `@medusajs/notification-local` was added as an explicit direct dependency (it was already present transitively via `@medusajs/medusa`, but the config resolves its import path directly, so it's declared honestly rather than relying on hoisting).

**Why:** the same "layer custom modules only where Medusa has no native equivalent" discipline that shaped every earlier custom module (`product-listing` on native `product`, `category-translation` on native `product_category`) applies just as much to *not* building something custom - saved addresses and admin user/invite management needed no backend work at all, and notifications needed only a thin dedup/inbox layer on top of Medusa's own send mechanic, not a parallel one.

**How to apply:**
- Before building a custom backend feature, check whether Medusa's native modules (or their official provider packages) already cover it - `node_modules/@medusajs/medusa/dist/api/admin/**` and `.../store/**` are the fastest way to check what native routes already exist before writing a new one.
- Any future transactional-notification event should call `recordNotification()` from a step added directly to the workflow that already performs the underlying action, not a separate subscriber - this project doesn't use Medusa's event-subscriber pattern anywhere else, and introducing it for notifications alone would be a second, inconsistent way of triggering side effects.

## Full product-content translation, CI pipeline, and an honest accounting of production readiness

**Date:** same window, Phase 11-12 combined ("Batch 5: Production Readiness and Launch Prep" per the user's 5-batch plan for the remaining phases - the final batch).

**Decision / key choices:**

1. **A new `product-translation` module gives products the same seller-submits/admin-approves moderation lifecycle as `product-listing` itself**, not the simpler "admin writes directly, immediately live" shape `category-translation` uses - `category_translation` is platform-owned/admin-authored, but product titles/descriptions are seller-authored content that needs the same review gate as the product listing itself (see `docs/PRD.md` §9.24, CLAUDE.md §Localization). Status enum is `draft|pending_review|approved|rejected` (no `archived` - that concept belongs to the whole product, not one locale's translation row) with the identical resubmit-after-rejection rule as `product_listing` (`rejected` → `draft` only, never straight back to `pending_review`).
2. **No composite unique DB index on `(product_id, locale)`** - same accepted-risk precedent as `category_translation`, which also has no DB-level uniqueness constraint on `(category_id, locale)` despite conceptually needing one; both rely entirely on a single service method (`upsertDraft()`/`upsertTranslation()`) being the only writer that ever creates a row for a given key, checking-then-writing rather than relying on the database to reject a duplicate. This is a real, if narrow, latent risk (a second writer added later without going through that method could create a duplicate row) - flagged here explicitly since it's now been repeated twice, not introduced fresh.
3. **The public product-detail route resolves an approved translation for `?locale=`, with English fallback** - identical pattern to categories' own locale resolution. **Explicit scope boundary:** the search/discovery results grid (`GET /products`, `PostgresSearchService`) does not resolve product translations - only the single-product detail page does. Extending search would mean joining translations into the live-query Postgres adapter (or waiting for the already-planned move to a ranked/indexed adapter, see the product-discovery slice's own decision entry) - flagged as real future work, not silently dropped.
4. **A fourth workflow-definition bug class was ruled out, not found, this batch** - every new/changed workflow file (`approve-product-translation.ts`, `reject-product-translation.ts`) was checked against `npx medusa db:migrate` (now a standard step after any workflow change, per the lesson from Batch 3/4) before being considered done, and it passed cleanly both times.
5. **A genuine, if narrow, security/accessibility review pass was done, not skipped or fabricated:** a targeted grep across every `src/api/seller/**` route for vendor-scoping confirmed the two files without an explicit `vendor_id`/`vendorId` string match are both legitimate (`seller/categories` is genuinely platform-owned read-only data; `seller/stripe/onboarding-link` derives `sellerId` from the session under a differently-named variable) - no gap found. A real accessibility gap **was** found and fixed: both notification-list components (storefront, seller-portal) used a clickable `<li>` with an `onClick` handler and no keyboard/button semantics - fixed by making the clickable row a real `<button>` element (focus ring, `disabled` when already read, keyboard-operable by construction).
6. **`apps/backend/src/scripts/check-production-readiness.ts`, built in an earlier phase ahead of when it was needed, was run and its output recorded honestly, not assumed**: as of this batch, exactly one business-config value remains at a placeholder default (`shipping.standard_shipping_fee_cents = 725`), and every real-money/real-communication feature flag (`live_payments_enabled`, `real_transfers_enabled`, `real_payouts_enabled`, `real_refunds_enabled`, `real_tax_calculation_enabled`, `real_email_enabled`, `real_sms_enabled`, `real_courier_booking_enabled`, `promotional_codes_enabled`) is still `false`. This one remaining placeholder is a genuine business/pricing decision this session has no authority to make - same category as every other `is_placeholder: true` value resolved throughout the project, left as-is rather than arbitrarily "finalized."
7. **A CI pipeline (`.github/workflows/ci.yml`) was written and is real, checked-in config - not a stub.** Two jobs: (a) lint/typecheck/unit-test/build across every workspace via the existing root `turbo`-orchestrated scripts, and (b) the full backend integration suite against a real `postgres:16` GitHub Actions service container, with `ENABLE_TEST_SUPPORT_ROUTES=true` (the same network-free fake Stripe client used locally - no Stripe key of any kind, live or test, is ever configured in CI). This directly addresses why this development machine's memory pressure has repeatedly prevented the integration suite from completing locally: a CI runner has more consistent memory headroom, so this pipeline is expected to be where those three deferred integration-test files (`checkout.spec.ts`, `fulfillment.spec.ts`, `seller-finance.spec.ts`) finally get to run to completion, not a local machine.
8. **What is honestly NOT achievable by an agent working in this local sandbox, and is recorded as such rather than silently declared "done" or fabricated:** real load testing (needs a running deployed instance and a load-generation tool actually hitting it under sustained traffic), a real staging deployment/soak test (needs a real staging *environment* to exist - cloud infrastructure this session has no access to provision), and any further business-config placeholder resolution beyond what an engineering session can decide unilaterally (commission rate, shipping fee, and every other `is_placeholder: true` value are business/legal decisions, not code). These are exactly the kind of destructive-or-external-system actions this project's own operating rules require a human to actually perform - see CLAUDE.md's action-category rules on "hard-to-reverse operations" and "actions visible to others or that affect shared state."

**Why:** this batch's job is to make the gap between "everything an agent can build and verify" and "what a human still has to do before a real launch" completely explicit, not to paper over it - a false "production ready" claim would be far more dangerous than an honest, itemized list of exactly three things (real load test, real staging soak, remaining business-config decisions) that remain.

**How to apply:**
- Any future custom translation table (or any other "logically unique per composite key, single writer" table) should either add the explicit unique index this batch and `category_translation` both went without, or explicitly accept and document the same narrow risk - don't silently repeat the omission a third time without at least naming it.
- Before claiming any project is "production ready," run `npx medusa exec ./src/scripts/check-production-readiness.ts` and report its actual output verbatim - never assert placeholder-free business configuration without having just checked.
- CI (`.github/workflows/ci.yml`) is the right place to finally get a passing run of the three integration-test files this development machine's memory pressure has prevented from completing locally (`checkout.spec.ts`, `fulfillment.spec.ts`, `seller-finance.spec.ts`) - check its results there rather than continuing to retry locally.
- Load testing and a staging soak test are not skippable "later" - they are two of the three explicitly named remaining gates before a real production launch (the third being resolving the one remaining business-config placeholder), and none of the three can be closed by an agent working alone in a local sandbox.
